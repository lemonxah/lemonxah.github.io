Expand description

Serializable ECS component data; blanket-implements Component. Native systems registered on ComponentRegistry implement runtime behavior. Inspector UI and gizmos live in zestengine-editor. Data must be Send + Sync; thread-confined runtime state belongs outside component data.

A component is a struct that is Serialize + Deserialize + Default, with a stable NAME. It holds data only: behaviour lives in systems that query the type. Fields not marked #[serde(skip)] are saved in scenes and shown in the inspector; #[serde(skip)] fields are runtime state.

ⓘ
#[derive(Serialize, Deserialize)]
pub struct Rotator { pub degrees_per_second: f32 }

impl Default for Rotator {
    fn default() -> Self { Self { degrees_per_second: 45.0 } }
}

impl TypedComponent for Rotator {
    const NAME: &'static str = "Rotator";
}

registry.register_ecs::<Rotator>();

Optionally expose actions and properties so the editor’s event bindings (and WASM scripts) can call and read the component.

See Components in the ECS guide.

const NET_ROLE: NetRole = NetRole::Both

Where this type exists by default (NET-3): Client types are stripped from a dedicated server, Server types from players. A scene can override it per component. The built-ins are classified in net_role::builtin_default_role (used while this stays Both).

fn predictable(&self) -> Option<&dyn Predictable>

A movement component that implements Predictable returns Some(self) from this and Self::predictable_mut: an owner-predicted NetworkObject carrying it then moves at once on its owner and is reconciled against the host, like the built-in controllers.
