ZestEngine Documentation

ZestEngine is a Vulkan game engine written in Rust, with a built-in editor, VR support, realtime global illumination, physics, networking and a sandboxed WebAssembly scripting layer. Gameplay code is plain Rust: components hold data, systems hold behaviour, and entities are ready-made objects you place in a scene or spawn from code.

Your first system in 30 seconds

In the editor, open the Files panel, right-click, and choose Create → New Rust → Component, then New Rust → System. The engine writes starter files into your project's plugins/components crate and registers them in its lib.rs. Put data in the component, behaviour in the system:

fn rotate(world: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    for (_, (owner, rotator)) in world.query::<(&Owner, &Rotator)>().iter() {
        if !ctx.is_active(world, owner.0) { continue; }
        let mut transform = world.get_mut::<Transform>(owner.0).expect("every object has a Transform");
        let step = Quat::from_rotation_y(rotator.degrees_per_second.to_radians() * ctx.dt);
        transform.rotation = (step * transform.rotation).normalize();
    }
}

Then Tools → Build & Reload Components, add the component to an object and press Play. The ECS Guide explains every line.

What is ZestEngine

ZestEngine is a standalone 3D game engine in Rust + Vulkan with a dockable in-engine editor. It's a general-purpose desktop + VR engine: scenes, materials, FBX/glTF import, a component + hot-reloadable Rust-plugin system, custom shaders and a visual shader graph, realtime global illumination (Flux), a lighting bake, audio (Steam Audio + voice chat), physics (rapier3d), water simulation, networking, OpenXR VR, and building standalone games straight from the editor.

Getting started

Development commands

The root justfile follows the same workflow as ZestBay. It requires just, Bash, Python 3.11+ (for tomllib), and the Rust toolchain. Native builds also need glslc, the Vulkan loader/drivers, ALSA and udev development libraries, and libclang for Steam Audio's bindings. Steam Audio's SDK downloads on its first build.

Installation puts the editor, hub, relay and libphonon.so together under <prefix>/lib/zestengine, links them in <prefix>/bin, and installs a desktop launcher + icons. just install targets /usr via sudo by default; for a user install use just install prefix="$HOME/.local" sudo="" and put $HOME/.local/bin on PATH. Keep this source checkout available: generated game projects use local engine crate paths. The install is a local developer install.

bump changes [workspace.package].version (inherited by the engine crates) and updates the lockfile offline; the example plugin and standalone game examples keep their independent versions. release requires a clean working tree, a branch with an upstream, and authenticated gh. It commits the version files, creates v<version>, pushes the branch and that tag to origin, then creates a GitHub release with generated notes. It does not upload build artifacts.

Building a game

From the editor: File → New Project to scaffold one, File → Project Settings to pick the boot scene, File → Build Game to produce build/<game> + build/assets/. The same is available headless:

zestengine --new-project <parent-dir> <name>   # scaffold a project
zestengine --build [project-dir]                # cargo build --release + bundle assets
zestengine --build <dir> --target windows       # cross-compile with cargo xwin

Windows builds need cargo install cargo-xwin and rustup target add x86_64-pc-windows-msvc (also available in the editor as File → Build Game for Windows). The output build/ folder is self-contained and relocatable; run the executable inside it.

ECS tutorial: a coin collector

This tutorial builds one small feature end to end: the player walks into coins, the coins vanish, and a score on screen goes up. It uses every part of the ECS once (components, systems, events, contacts, registration, the editor, a test), so it is the quickest way to see how the pieces fit before reading the ECS Guide in full.

The code on this page was compiled and run against zestengine-core, including the test at the end.

Before you start

You need a project with a plugins/components crate (File → New Project creates one, see Getting started). All of the code below goes in one new file, plugins/components/src/coin_collector.rs.

Step 1: the data

Components are plain structs that implement TypedComponent. They must be Serialize + Deserialize + Default.

use serde::{Deserialize, Serialize};
use zestengine_core::ecs::{ContactPhase, EcsMoveHost, SceneEvent, Stage, run_ordered};
use zestengine_core::{ComponentRegistry, MoveHost, ObjectId, TypedComponent, UiText};

/// Marker: objects that can pick coins up. It has no data; its presence is the data.
#[derive(Default, Serialize, Deserialize)]
pub struct Collector {}

impl TypedComponent for Collector {
    const NAME: &'static str = "Collector";
}

/// A pickup worth `value` points.
#[derive(Serialize, Deserialize)]
pub struct Coin {
    pub value: u32,
}

impl Default for Coin {
    fn default() -> Self { Self { value: 1 } }
}

impl TypedComponent for Coin {
    const NAME: &'static str = "Coin";
}

/// Shows the score in this object's `UiText`.
#[derive(Default, Serialize, Deserialize)]
pub struct ScoreBoard {
    #[serde(skip)]
    pub score: u32,
}

impl TypedComponent for ScoreBoard {
    const NAME: &'static str = "Score Board";
}

Three things to notice:

  • NAME is permanent. It is how the Add Component menu, the .scene file and event bindings refer to the type. Pick it once.
  • value is saved; score is not. Everything without #[serde(skip)] is written to the scene and shown in the inspector, so a designer can make a 10-point coin. score is scratch state that only exists while playing, so it is #[serde(skip)].
  • Collector is empty on purpose. A "tag" component is the ECS way to say this object is a kind of thing. Systems then ask "does the other object carry a Collector?".

Imports. MoveHost looks unused, but it is the trait that provides self_id() and the transform helpers on host. If the compiler says "no method named self_id", this import is missing.

Step 2: the event

An event is any 'static type. Declare it next to the code that emits it:

/// Event: `by` picked up something worth `value`.
pub struct Collected {
    pub by: ObjectId,
    pub value: u32,
}

It refers to objects by ObjectId, the stable UUID every object has and scenes save, rather than by a runtime handle.

Step 3: the pickup system

When two colliders touch, the engine reports a contact to both objects during the Events stage. The system looks for contacts where this coin was entered by something that is a Collector:

registry.register_system_for::<Coin>("game::coin_pickup", Stage::Events, |world, ctx| {
    let contacts = ctx.services.scene_events;
    run_ordered(world, ctx, |coin: &mut Coin, host| {
        let me = host.self_id();
        for contact in contacts {
            if let SceneEvent::Contact { object, other, trigger: true, phase: ContactPhase::Enter, .. } = contact
                && *object == me
                && host.get::<Collector>(*other).is_some()
            {
                host.emit(Collected { by: *other, value: coin.value });
                host.destroy_self();
            }
        }
    })
});

Reading it line by line:

  • register_system_for::<Coin> runs the system only while at least one enabled Coin exists, so a level without coins pays nothing.
  • run_ordered calls the closure once per active Coin, in scene order, with the component and an EcsMoveHost (host) bound to that coin's object. Disabled objects are skipped for you.
  • ctx.services.scene_events is this frame's list of contacts. The pattern keeps only trigger overlaps (trigger: true) that just started (ContactPhase::Enter), where the receiver (object) is this coin.
  • host.get::<Collector>(*other) reads a component from the other object. It returns None if the object has none, so a crate or a wall touching the coin is ignored.
  • host.emit(..) broadcasts the event. host.destroy_self() queues the coin for removal; it disappears when the stage ends.

Step 4: the score system

The score board reads Collected events and writes the total into a UiText. UI elements are components like any other, so updating them is an ordinary edit:

impl ScoreBoard {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        for collected in host.events::<Collected>() {
            self.score += collected.value;
        }
        let id = host.self_id();
        let text = format!("Score {}", self.score);
        host.edit::<UiText>(id, move |ui| ui.text = text);
    }
}

registry.register_system_for::<ScoreBoard>("game::score_board", Stage::LateUpdate, |world, ctx| {
    run_ordered(world, ctx, ScoreBoard::update)
});

LateUpdate is the right stage for anything that mirrors the frame's final state onto the screen. host.edit::<UiText>(id, ..) changes the UiText on the same object as the ScoreBoard, so put both components on one object.

What happens, frame by frame

frame N    FixedUpdate   physics step: the player overlaps the coin's trigger
           Events        game::coin_pickup sees Contact(Enter)

                           queue Destroy(coin)  → applied when the stage ends

Two rules from the ECS Guide explain the one-frame gap between the pickup and the new score: an event emitted in frame N is readable throughout frame N + 1, and never in the frame that emitted it. Neither system ever touches the other's data.

Step 7: test it without a window

Systems are plain functions over a world, so you can test them headlessly: no GPU, no window, no engine loop. Build a SceneWorld, register your code, run a stage, and look at the data and at the commands the systems queued. First a small harness (it is the one from Testing systems):

use zestengine_core::ecs::{ContactPhase, SceneEvent, SceneWorld, Stage, SystemContext};
use zestengine_core::{AnyBox, ComponentCommand, ComponentRegistry, InputState, ObjectId, UiText};

#[derive(Default)]
struct Frame {
    dt: f32,
    input: InputState,
    events: Vec<AnyBox>,
    scene_events: Vec<SceneEvent>,
}

/// Run every system registered for `stage` once and return the commands they queued.
fn run(registry: &ComponentRegistry, scene: &SceneWorld, stage: Stage, frame: &Frame) -> Vec<ComponentCommand> {
    let mut commands = Vec::new();
    let mut ctx = SystemContext::new(&frame.input, &mut commands);
    ctx.dt = frame.dt;
    ctx.services.events = &frame.events;
    ctx.services.scene_events = &frame.scene_events;
    registry.run_systems(stage, scene, &mut ctx);
    commands
}

fn destroyed(commands: &[ComponentCommand]) -> Vec<ObjectId> {
    commands.iter().filter_map(|c| match c { ComponentCommand::Destroy(id) => Some(*id), _ => None }).collect()
}

fn emitted<E: 'static>(commands: &[ComponentCommand]) -> Vec<&E> {
    commands.iter().filter_map(|c| match c { ComponentCommand::Emit(event) => event.0.downcast_ref::<E>(), _ => None }).collect()
}

fn event<E: 'static>(value: E) -> AnyBox { AnyBox(Box::new(value)) }

Then the test. You fake what the engine would hand the systems (a contact, last frame's events) and check what comes out:

#[test]
fn collecting_a_coin_scores_next_frame() {
    let mut registry = ComponentRegistry::default();
    register(&mut registry);

    let mut scene = SceneWorld::new();
    let coin = scene.spawn("Coin");
    let player = scene.spawn("Player");
    let board = scene.spawn("Board");
    scene.insert(coin, Coin { value: 5 }).unwrap();
    scene.insert(player, Collector {}).unwrap();
    scene.insert(board, ScoreBoard::default()).unwrap();
    scene.insert(board, UiText::default()).unwrap();
    let coin_id = scene.object_id(coin).unwrap();
    let player_id = scene.object_id(player).unwrap();
    let board_id = scene.object_id(board).unwrap();

    // The physics engine reports "`other` entered the coin's trigger".
    let touch = |other| SceneEvent::Contact {
        object: coin_id,
        other,
        trigger: true,
        phase: ContactPhase::Enter,
        two_dimensional: false,
    };

    // Something that is not a Collector touches the coin: nothing happens.
    let ignored = run(&registry, &scene, Stage::Events, &Frame { scene_events: vec![touch(board_id)], ..Default::default() });
    assert!(ignored.is_empty());

    // The player touches it: the coin is destroyed and a Collected event is announced.
    let commands = run(&registry, &scene, Stage::Events, &Frame { scene_events: vec![touch(player_id)], ..Default::default() });
    assert_eq!(destroyed(&commands), [coin_id]);
    let collected = emitted::<Collected>(&commands);
    assert_eq!((collected[0].by, collected[0].value), (player_id, 5));

    // Next frame the score board reads the events and updates its text.
    let events = vec![event(Collected { by: player_id, value: 5 }), event(Collected { by: player_id, value: 10 })];
    run(&registry, &scene, Stage::LateUpdate, &Frame { events, ..Default::default() });
    assert_eq!(scene.get::<UiText>(board).unwrap().text, "Score 15");
}

The harness does not apply queued commands, so you assert on the commands themselves (Destroy, Emit) and feed events back in by hand. That keeps each test about one system and one frame.

ZestEngine ECS Guide

How game logic is written in ZestEngine: components hold data, systems hold behaviour, and entities are ready-made objects you can place in a scene or spawn from code. This guide explains the model, then walks through the patterns that real games are made of: moving a player, taking damage, spawning things, picking up coins, opening doors, shooting.

Every example in this guide is compiled and run by crates/zestengine-core/tests/ecs_guide.rs, so the code you copy works. Companion guides: ENGINE_API.md (what you can do from a system: move, spawn, raycast, play sounds, …) and WASM.md (sandboxed scripts for user-generated content). The generated API reference is at api/zestengine_core.

The big picture

ZestEngine's gameplay layer is an entity-component-system built on hecs. The vocabulary maps like this:

ConceptIn ZestEngineWhere
EntityAn object in the scene tree: a transform plus whatever components you attach. Saved with a stable ObjectId (UUID).SceneWorld
ComponentA plain Rust struct implementing TypedComponent: serializable data, shown in the inspector.TypedComponent
SystemA function fn(&SystemWorld, &mut SystemContext) that queries components and changes them.SystemFn
StageThe point in the frame a system runs: Start, FixedUpdate, Update, Gameplay, LateUpdate, Events.Stage
CommandA request that changes the wider world (spawn, destroy, play a sound, load a scene). Queued by systems, applied at the end of the stage.ComponentCommand
EventA value any system can broadcast (ctx.emit) and any system can read next frame (ctx.events).SystemContext
Entity templateA named, ready-made object (mesh shape + starting components) registered by your project.EntityTemplate

A word on naming. In ECS terms every scene object is an entity. In the New Rust menu, Entity means the ready-made kind: a template such as "Enemy" or "Crate" that appears under Create → Entity and can be spawned from code. This guide says object for the scene-tree thing and entity for the template.

Three rules shape everything else:

  1. Data lives in components, behaviour lives in systems. A component never has an update method that the engine calls. Systems find components by querying for them.
  2. Systems edit component data directly; they ask for everything else. Changing a Transform or a Health is an ordinary write. Spawning, destroying, sounds, scene loads and physics pushes are queued as commands, so the world never changes underneath a running query.
  3. Systems run only while playing. The editor's Play mode and a shipped game run the same loop. While you author a scene, nothing ticks.

Objects

An object is a hecs entity carrying a fixed set of built-in components, plus the ones you attach:

Built-in componentMeaning
ObjectIdStable UUID. Saved in scenes, used by ObjectRef fields and the network. Survives reloads and reordering.
NameThe display name. Cosmetic: not unique.
TransformLocal translation / rotation / scale (relative to the parent).
ParentThe parent object, if any.
EnabledThe checkbox in the inspector.
ActiveEnabled and every ancestor enabled. Computed; skip objects where it is false.
GlobalTransformWorld matrix as of the last hierarchy propagation (a snapshot, refreshed at each stage boundary).
OwnerThe object a component instance belongs to. Objects own themselves.

Two details matter in practice.

Local versus world. Transform is local. When you need a true world position, ask the host (host.world_position(), host.position_of(target)) or world.world_transform(entity), which folds in every parent including writes made earlier in the same stage. GlobalTransform is only a snapshot.

Duplicate components. An object can carry two components of the same type. The first lives on the object's own hecs entity; later ones live on small auxiliary entities that point back with Owner. That is why systems query (&Owner, &T) rather than &T: Owner is how you get from a component back to its object (for the transform, the Active flag, the ObjectId).

for (_, (owner, rotator)) in world.query::<(&Owner, &Rotator)>().iter() {
    let object: hecs::Entity = owner.0;            // the object this Rotator is on
    let id = world.object_id(object);              // its saved ObjectId
}

You almost never build objects by hand in game code. The editor builds them from scenes, and systems spawn them with commands (see Spawning and destroying). Tests use SceneWorld directly (see Testing systems).

Components

A component is a struct that implements TypedComponent. It must be Serialize + Deserialize + Default + Send + Sync + 'static.

use serde::{Deserialize, Serialize};
use zestengine_core::TypedComponent;

/// Spins the object around the Y axis.
#[derive(Serialize, Deserialize)]
pub struct Rotator {
    pub degrees_per_second: f32,
}

impl Default for Rotator {
    fn default() -> Self { Self { degrees_per_second: 45.0 } }
}

impl TypedComponent for Rotator {
    const NAME: &'static str = "Rotator";
}

Rules of thumb:

  • NAME is permanent. It is the identity used by the Add Component menu, the .scene file and event bindings. Renaming it orphans saved data. If you must, keep the old one in ALIASES.
  • Saved versus runtime fields. Everything that is not #[serde(skip)] is saved in the scene and shown in the inspector. Mark scratch state (timers, "have I started", cached positions) #[serde(skip)]; it keeps its value while playing and resets when a plugin reloads or a scene loads.
  • Vectors. The workspace builds glam without its serde feature, so saved fields use arrays ([f32; 3]) and runtime-only fields use Vec3/Quat with #[serde(skip)].
  • References to other objects are ObjectRef fields (ObjectRef::NONE when unset). The inspector renders a drop target; at runtime you resolve it with host.get::<T>(self.target), host.position_of(self.target), and so on. They return None when the target is unset or was deleted, so always handle that case.
  • Add #[serde(default)] to a component's struct when you expect to add fields later: old scenes keep loading.
  • Network role. const NET_ROLE (default Both) says where a type exists: Client types are stripped from a dedicated server, Server types from players.
  • Disabled instances. Switching a component off in the inspector moves its value into a DisabledComponent<T> column. Ordinary T queries (and register_system_for::<T>) see only enabled instances; the value, including runtime state, is kept for when it is switched back on.

Register the type so scenes can load it and systems can query it:

registry.register_ecs::<Rotator>();   // `register::<T>()` is the same call

Actions and properties

Components can expose actions (functions) and properties (readable values) to the editor's event bindings: "when the player enters this trigger, call Door → Open". Declare them as static tables and implement three methods. This is also what makes a component callable from a WASM script.

use zestengine_core::{ActionCtx, ActionDesc, ActionType, ArgValue, ParamDesc, PropertyDesc};

static DOOR_ACTIONS: &[ActionDesc] = &[
    ActionDesc::new("Open", "Open", &[], true),
    ActionDesc::new("Close", "Close", &[], true),
    ActionDesc::new("SetSpeed", "Set Speed", &[ParamDesc::float("speed", 2.0)], true),
];
static DOOR_PROPERTIES: &[PropertyDesc] = &[PropertyDesc::new("open", ActionType::Bool)];

impl TypedComponent for Door {
    const NAME: &'static str = "Door";

    fn actions(&self) -> &'static [ActionDesc] { DOOR_ACTIONS }
    fn properties(&self) -> &'static [PropertyDesc] { DOOR_PROPERTIES }

    fn read_property(&self, property: &str) -> Option<ArgValue> {
        (property == "open").then_some(ArgValue::Bool(self.wants_open))
    }

    fn invoke_action(&mut self, _ctx: &mut ActionCtx<'_>, action: &str, args: &[ArgValue]) -> Result<(), String> {
        match action {
            "Open" => self.wants_open = true,
            "Close" => self.wants_open = false,
            "SetSpeed" => self.speed = args[0].as_f32().max(0.0),
            _ => return Err(zestengine_core::actions::unknown_action(Self::NAME, action)),
        }
        Ok(())
    }
}
  • An action's name is permanent for the same reason NAME is; the label is what the editor shows.
  • The last argument of ActionDesc::new is ugc_safe. Mark an action safe only if it cannot change scenes, hurt other players or leave the world. The editor's content-authoring dropdowns offer only safe actions, and sandboxed WASM modules in untrusted content can expose only safe ones; mods may additionally call only the actions the game's allow-list names. See ugc_safe in the WASM Guide for exactly what is enforced where.
  • Arguments arrive already coerced to the declared types and as long as the parameter list, so args[0] is safe to index.
  • An action cannot read itself back through a property reader while it runs, but it can read other components, including other instances of its own type. ctx.emit(event) and ctx.commands work inside actions.

Systems

A system is a plain function. It receives a read-only view of the world (components are borrowed through it) and a per-frame context.

use glam::Quat;
use zestengine_core::Transform;
use zestengine_core::ecs::{Owner, Stage, SystemContext, SystemWorld};

fn rotate(world: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    for (_, (owner, rotator)) in world.query::<(&Owner, &Rotator)>().iter() {
        if !ctx.is_active(world, owner.0) { continue; }
        let mut transform = world.get_mut::<Transform>(owner.0).expect("every object has a Transform");
        let step = Quat::from_rotation_y(rotator.degrees_per_second.to_radians() * ctx.dt);
        transform.rotation = (step * transform.rotation).normalize();
    }
}

Register it on the ComponentRegistry, together with its component:

pub fn register(registry: &mut ComponentRegistry) {
    registry.register_ecs::<Rotator>();
    registry.register_system_for::<Rotator>("game::rotate", Stage::Update, rotate);
}
RegistrationRuns the system
register_system(name, stage, f)Every time the stage runs.
register_system_for::<T>(name, stage, f)Only while at least one enabled T exists. Use this by default: unused features cost nothing.
register_system_if(name, stage, f, condition)Only while condition(world) is true. Used for start-up work (see Timers and state).

Names are unique. Registering an existing name replaces the code and stage in place (that is how a hot-reloaded plugin supersedes its old build). The function type is a plain fn pointer, so a system cannot capture variables: keep state in components, not in closures. (A non-capturing closure, like the |world, ctx| run_ordered(...) forms below, coerces to a fn.)

The comfortable way: run_ordered and EcsMoveHost

Most gameplay code wants "for each active instance of my component, in scene order, with helpers for this object". That is run_ordered, which gives your closure the component and an EcsMoveHost: the per-object toolbox for moving, reading other objects, spawning, physics queries, sounds and more. It also dereferences to the SystemContext, so host.dt, host.input and host.emit(..) all work.

use glam::Vec3;
use zestengine_core::MoveHost;                       // translation(), set_translation(), world_position(), …
use zestengine_core::ecs::{EcsMoveHost, run_ordered};

#[derive(Serialize, Deserialize)]
pub struct PlayerMover {
    pub speed: f32,
}

impl PlayerMover {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        let direction = host.input.axis2("Move"); // x = right, y = forward
        let step = Vec3::new(direction.x, 0.0, -direction.y) * self.speed * host.dt;
        let position = host.translation() + step;
        host.set_translation(position);
    }
}

registry.register_system_for::<PlayerMover>("game::player_mover", Stage::Update, |world, ctx| {
    run_ordered(world, ctx, PlayerMover::update)
});

run_ordered does three things a hand-written loop does not:

  • skips inactive objects (disabled, or under a disabled parent);
  • iterates in scene order, so behaviour is deterministic. That matters for networking, prediction replay and anything where two objects interact within one frame. A bare world.query iterates in archetype order, which is an implementation detail;
  • hands you an EcsMoveHost bound to the object.

Use a bare query when order is irrelevant and you have thousands of instances (it avoids collecting and sorting); use run_ordered otherwise. The full method list of EcsMoveHost is in ENGINE_API.md.

Borrowing rules

hecs checks borrows at run time, per component column, and the engine adds a lock for structural changes. The rules that matter:

  • Two borrows of the same component type conflict if either is mutable. world.get_mut::<Transform>(e) inside a query that already borrows Transform panics with … already borrowed. Nested queries are fine when they borrow different components (the poison zone example below).
  • No structural changes inside a system. You cannot insert, remove or despawn components or objects through the world while a system runs. The world is locked, and the call panics with structural ECS access while component views are borrowed. Spawn and destroy with commands.
  • Use the SystemWorld you were given. Editor-style component views (SceneWorld::get, ComponentSet::get_typed) panic inside a system with component-view access during native ECS execution.
  • A panic in a system is not swallowed. Locks are released and component values stay intact, but the panic propagates, so treat expect like any other assertion.

When two of your own systems need the same data, run them in different stages or let one emit an event for the other (see Events).

Stages

A frame runs the stages in this order. After each stage the engine applies the commands it queued.

tick(dt)
 ├─ Start          repeats (up to 8×) while start-up work keeps spawning objects
 ├─ animation markers ──▶ Events stage (SceneEvent::Animation)
 ├─ FixedUpdate  ┐ 0 to 8 times per frame at a fixed 60 Hz, dt = 1/60
 │  physics step ┘
 ├─ contacts ───────────▶ Events stage (SceneEvent::Contact, 3D then 2D)
 ├─ Update
 ├─ Gameplay
 ├─ navigation agents move, animators evaluate
 └─ LateUpdate
StageUse it for
StartInitialising new instances: capture a rest position, cache a reference, spawn initial children. Not called "once" by the engine: guard with a flag (see Timers and state).
FixedUpdateContinuous forces and anything that must match the physics rate. Runs before each physics step with dt = 1/60.
UpdateMovement and general per-frame logic: controllers, AI steering, input handling.
GameplayLogic that must see movement already resolved: weapons, damage, pickups, health. Runs after Update's movement commands (a character move, a teleport) have been applied.
LateUpdateThings that read the final pose of the frame: cameras following a target, HUD bindings. Runs after animation and navigation.
EventsReacting to contacts and animation markers through ctx.services.scene_events. Runs when such events exist.

ctx.dt is unscaled_dt × time_scale, and the engine clamps a single frame to 0.25 s so a hitch cannot teleport everything.

Commands

Anything that reaches outside component data is a ComponentCommand pushed onto ctx.commands. The engine applies them, in order, right after the stage that queued them:

ctx.commands.push(ComponentCommand::Destroy(object_id));
ctx.commands.push(ComponentCommand::PlaySound { clip: "audio/pop.ogg".into(), position: None, volume: 1.0 });

EcsMoveHost wraps the common ones in readable methods (host.destroy(target), host.play_sound_at(..), host.add_impulse(..)), which is usually what you want. Two properties to remember:

  • Queued means "after this stage". host.destroy_self() does not remove the object while your system is still iterating; it disappears when the stage ends. Systems later in the same stage still see it.
  • Bad targets are ignored. A command that names an object that no longer exists does nothing.

Direct writes to component data (host.edit::<T>(target, |t| ..), host.set_translation(..)) are immediate and visible to systems that run later in the same stage. The full list of commands and which host methods queue them is in ENGINE_API.md.

Events

There are three ways for systems to react to something that happened.

Broadcast events

Any 'static type is an event. A system emits one; every system can read it next frame. The sender and the receiver never touch each other's data, which is the whole point.

/// Event: something hit `target` for `amount`.
pub struct Hit { pub target: ObjectId, pub amount: f32 }
/// Event: the object ran out of hitpoints.
pub struct Died { pub object: ObjectId }

#[derive(Serialize, Deserialize)]
pub struct Hitpoints { pub current: f32, pub max: f32 }   // Default: 100 / 100

fn apply_hits(world: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    // Events emitted during the previous frame are readable now.
    let hits: Vec<&Hit> = ctx.events::<Hit>().collect();
    if hits.is_empty() { return; }
    for (_, (owner, hp)) in world.query::<(&Owner, &mut Hitpoints)>().iter() {
        let Some(me) = world.object_id(owner.0) else { continue };
        let before = hp.current;
        for hit in hits.iter().filter(|hit| hit.target == me) {
            hp.current = (hp.current - hit.amount).max(0.0);
        }
        if before > 0.0 && hp.current == 0.0 {
            ctx.emit(Died { object: me }); // readable next frame
        }
    }
}

fn remove_the_dead(_: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    for died in ctx.events::<Died>() {
        ctx.commands.push(ComponentCommand::Destroy(died.object));
    }
}

registry.register_system_for::<Hitpoints>("game::apply_hits", Stage::Gameplay, apply_hits);
registry.register_system("game::remove_the_dead", Stage::Gameplay, remove_the_dead);

An event emitted in frame N is readable throughout frame N + 1; an event you emit is not visible to you in the same frame. The engine's own systems use the same bus: weapons emit DamageEvent, health emits DeathEvent, target dummies emit ScoreEvent, animators emit AnimatorStateChanged and AnimationEvent, and the HUD reads them. Subscribing to those from your own systems is just ctx.events::<DamageEvent>().

Scene events: contacts and animation markers

Collisions, trigger overlaps and animation markers arrive within the frame in the Events stage, as ctx.services.scene_events:

use zestengine_core::ecs::{ContactPhase, SceneEvent};

#[derive(Default, Serialize, Deserialize)]
pub struct Collector {}                       // marker: can pick coins up

#[derive(Serialize, Deserialize)]
pub struct Coin { pub value: u32 }            // Default: value 1

/// Event: `by` picked up something worth `value`.
pub struct Collected { pub by: ObjectId, pub value: u32 }

registry.register_system_for::<Coin>("game::coin_pickup", Stage::Events, |world, ctx| {
    let contacts = ctx.services.scene_events;
    run_ordered(world, ctx, |coin: &mut Coin, host| {
        let me = host.self_id();
        for contact in contacts {
            if let SceneEvent::Contact { object, other, trigger: true, phase: ContactPhase::Enter, .. } = contact
                && *object == me
                && host.get::<Collector>(*other).is_some()
            {
                host.emit(Collected { by: *other, value: coin.value });
                host.destroy_self();
            }
        }
    })
});

Both objects of a touching pair receive a Contact event (object is the receiver, other the one it touched), with phase Enter, Stay (2D) or Exit, trigger telling a trigger overlap from a solid collision, and two_dimensional for 2D physics. The coin needs a collider with Is Trigger on; the player needs a collider and a rigid body or character.

Action bindings

The third way is data-driven: the inspector's Trigger Events, Interactable, UI Button and Animation Event Bindings components store lists of "call this action on that component" and the engine resolves and runs them. You get that for free for any component that declares actions. Gameplay that fires a binding from code uses queue_actions(&bindings, &FireSource { … }, ctx.commands).

Spawning and destroying

Spawning is a command; the call returns the new ObjectId immediately so you can wire it up, but the object exists from the next stage on.

let id = host.spawn_prefab("prefabs/enemy.prefab", position, rotation); // a .prefab asset
let id = host.instantiate(self.bullet_template, position, rotation);    // clone a scene object
let id = host.spawn_entity("Crate", position, rotation);                // a registered entity
host.net_spawn("prefabs/bullet.prefab", position, rotation);            // on every peer
host.destroy(target);                                                    // object and children
host.destroy_self();
host.set_active(door, false);                                            // disable without deleting

A timed self-destruct is the smallest useful spawn companion:

#[derive(Serialize, Deserialize)]
pub struct Lifetime { pub seconds_left: f32 }   // Default: 3.0

impl Lifetime {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        self.seconds_left -= host.dt;
        if self.seconds_left <= 0.0 {
            host.destroy_self();
        }
    }
}

Objects spawned during a frame run their Start systems before the next Update, so a freshly spawned object is initialised before it acts. See Entities for a spawner that drops crates.

Entities

An entity is a named, ready-made object: a mesh shape plus the components it starts with. Register it once; it then appears under Create → Entity in the editor and any system can spawn it by name.

use zestengine_core::ecs::{EntityShape, EntityTemplate};

/// The entity: a cube that deletes itself after ten seconds.
fn crate_entity() -> EntityTemplate {
    EntityTemplate::new(EntityShape::Cube).with(Lifetime { seconds_left: 10.0 })
}

registry.register_entity("Crate", crate_entity);
  • EntityShape is Empty, Cube, Sphere, Capsule or Plane. Empty makes a transform that only carries components (a spawner, a manager); the others also get a MeshRenderer with the default material.
  • .with(component) adds a component. Add as many as you like, in inspector order. The builder function runs for every new instance, so each object gets its own component values.
  • The name is the identity: spawn_entity("Crate", ..) and the menu both use it. Registering an existing name replaces the builder, and a plugin reload drops entities the plugin no longer exports.
  • An entity made in the editor is an ordinary scene object once placed: it saves as its components and mesh, and you can edit it freely.
  • On a dedicated server (no renderer) an entity still spawns, with its components and without a GPU mesh.

A spawner is just a component and a system:

#[derive(Serialize, Deserialize)]
pub struct CrateSpawner {
    pub every: f32,
    #[serde(skip)]
    pub timer: f32,
}

impl CrateSpawner {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        self.timer -= host.dt;
        if self.timer <= 0.0 {
            self.timer = self.every;
            let above = host.world_position() + Vec3::Y;
            host.spawn_entity("Crate", above, Quat::IDENTITY);
        }
    }
}

Talking to other objects

Systems often need another object's data: a follower needs its target's position, a turret needs its target's health. Reference the other object with an ObjectRef field and ask the host.

#[derive(Serialize, Deserialize)]
pub struct Follower {
    pub target: ObjectRef,
    pub speed: f32,
}

impl Follower {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        let Some(goal) = host.position_of(self.target) else { return }; // world position
        let here = host.world_position();
        let to_goal = goal - here;
        let step = self.speed * host.dt;
        if to_goal.length() <= step {
            host.set_world_position(goal);
        } else {
            host.set_world_position(here + to_goal.normalize() * step);
        }
    }
}

When one component should act on every object of another kind, query both. This swamp hurts anything with Hitpoints inside its radius; the nested query is legal because the two loops borrow different components:

fn poison(world: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    for (_, (owner, zone)) in world.query::<(&Owner, &PoisonZone)>().iter() {
        if !ctx.is_active(world, owner.0) { continue; }
        let Some(center) = world.world_transform(owner.0).map(|m| m.w_axis.truncate()) else { continue };
        for (_, (victim, hp)) in world.query::<(&Owner, &mut Hitpoints)>().iter() {
            let Some(at) = world.world_transform(victim.0).map(|m| m.w_axis.truncate()) else { continue };
            if at.distance(center) <= zone.radius {
                hp.current = (hp.current - zone.damage_per_second * ctx.dt).max(0.0);
            }
        }
    }
}

Input

Input is a snapshot of actions (named, rebindable), not raw keys: ctx.input is an InputState.

The default keyboard-and-mouse scheme defines Move (WASD), Look (mouse), Jump, Sprint, Crouch, Fire, Interact, Grab and Voice; the gamepad scheme uses the same names on its sticks and buttons, so code written against action names works on every device. Players can rebind them, and a game can define its own actions in its control scheme. An action that does not exist reads as "not pressed". When the player is typing into a UI text field, host.ui_text_editing() is true: skip gameplay input then.

For networked objects another peer may be driving, check host.driven_remotely() before applying local input, and host.has_authority(id) before changing shared state.

Physics and contacts

Physics queries are immediate; pushes are commands. A ray gun:

#[derive(Serialize, Deserialize)]
pub struct Laser { pub damage: f32, pub range: f32 }   // Default: 25 / 100

impl Laser {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        if !host.input.pressed("Fire") { return; }
        let aim = host.self_transform(); // world position and orientation
        let Some(hit) = host.raycast(aim.translation, aim.forward(), self.range) else { return };
        let damage = self.damage;
        host.edit::<Hitpoints>(hit.object, move |hp| hp.current = (hp.current - damage).max(0.0));
        host.add_impulse(hit.object, aim.forward() * 5.0);
        host.play_sound_at("audio/zap.ogg", hit.point, 1.0);
    }
}

host.raycast ignores triggers and the caller's own colliders; use raycast_filtered with a RayFilter for layer masks. Rigid bodies move through commands (add_force, add_impulse, set_velocity); characters through move_character. Contacts arrive as scene events. The ENGINE_API guide covers physics in full.

Timers and state

Three patterns cover most state.

A cooldown is a #[serde(skip)] float you count down, as in CrateSpawner::timer above.

A state machine is an enum field. Derive Serialize, Deserialize on the enum and give the component a Default; match on it in the system and change it as conditions are met.

Start-up work uses the Start stage. The engine does not call "start once per instance"; the stage simply runs before Update each frame, and your component remembers whether it has initialised. Register the system with register_system_if so it costs nothing once every instance has started:

#[derive(Serialize, Deserialize)]
pub struct Door {
    pub lift: f32,
    pub speed: f32,
    #[serde(skip)]
    pub wants_open: bool,
    #[serde(skip)]
    pub closed_y: Option<f32>,        // None until started
}

impl Door {
    /// Runs once for each new instance (Stage::Start): remember where "closed" is.
    fn start(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        if self.closed_y.is_none() {
            self.closed_y = Some(host.translation().y);
        }
    }

    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        let Some(closed) = self.closed_y else { return };
        let goal = if self.wants_open { closed + self.lift } else { closed };
        let mut position = host.translation();
        let step = self.speed * host.dt;
        position.y += (goal - position.y).clamp(-step, step);
        host.set_translation(position);
    }
}

registry.register_system_if(
    "game::door_start",
    Stage::Start,
    |world, ctx| run_ordered(world, ctx, Door::start),
    |world| world.query::<&Door>().iter().any(|(_, door)| door.closed_y.is_none()),
);
registry.register_system_for::<Door>("game::door", Stage::Update, |world, ctx| {
    run_ordered(world, ctx, Door::update)
});

The Door of the actions example is this same component: Open and Close set wants_open, and any trigger, button or WASM script can bind to them.

Showing state in the UI

UI elements are components too, so a system updates them like any other data:

/// Shows the score in this object's `UiText`.
#[derive(Default, Serialize, Deserialize)]
pub struct ScoreBoard {
    #[serde(skip)]
    pub score: u32,
}

impl ScoreBoard {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        for collected in host.events::<Collected>() {
            self.score += collected.value;
        }
        let id = host.self_id();
        let text = format!("Score {}", self.score);
        host.edit::<UiText>(id, move |ui| ui.text = text);
    }
}

registry.register_system_for::<ScoreBoard>("game::score_board", Stage::LateUpdate, |world, ctx| {
    run_ordered(world, ctx, ScoreBoard::update)
});

LateUpdate is the right stage for anything that mirrors the frame's final state onto the screen.

How a plugin gets into the game:

  • In the editor, Tools → Build & Reload Components compiles the crate with its editor feature and registers the new build over the old one. Component values are re-created from their serialized state, so #[serde(skip)] runtime fields reset on reload.
  • In a shipped game, src/main.rs calls zestengine_project_components::zestengine_register(registry) from run_game, linking the plugin statically (the editor feature, egui and the editor crate are not linked).
  • On a dedicated server, the built cdylib is listed in server.ron and loaded at start-up.
  • ABI stamp. export_plugin_abi!() lets a host refuse a plugin built with a different rustc, engine version or dependency features instead of crashing. Rebuild plugins and the engine together.

Testing systems

Systems are plain functions over a world, so they test without a window, a GPU or the engine loop. Build a SceneWorld, register your component and systems on a ComponentRegistry, run a stage, and look at the data and the queued commands. This is the harness the examples in this guide use:

use zestengine_core::ecs::{SceneEvent, SceneWorld, Stage, SystemContext};
use zestengine_core::{AnyBox, ComponentCommand, ComponentRegistry, InputState};

#[derive(Default)]
struct Frame {
    dt: f32,
    input: InputState,
    events: Vec<AnyBox>,
    scene_events: Vec<SceneEvent>,
}

/// Run every system registered for `stage` once and return the commands they queued.
fn run(registry: &ComponentRegistry, scene: &SceneWorld, stage: Stage, frame: &Frame) -> Vec<ComponentCommand> {
    let mut commands = Vec::new();
    let mut ctx = SystemContext::new(&frame.input, &mut commands);
    ctx.dt = frame.dt;
    ctx.services.events = &frame.events;
    ctx.services.scene_events = &frame.scene_events;
    registry.run_systems(stage, scene, &mut ctx);
    commands
}

#[test]
fn spins_active_objects_only() {
    let mut registry = ComponentRegistry::default();
    register(&mut registry);
    let mut scene = SceneWorld::new();
    let spinning = scene.spawn("Spinning");
    scene.insert(spinning, Rotator { degrees_per_second: 90.0 }).unwrap();
    run(&registry, &scene, Stage::Update, &Frame { dt: 1.0, ..Default::default() });
    let expected = Quat::from_rotation_y(90f32.to_radians());
    assert!(scene.get::<Transform>(spinning).unwrap().rotation.abs_diff_eq(expected, 1e-5));
}

Useful pieces:

  • SceneWorld::spawn, insert, get, get_mut, remove, set_parent, propagate build and inspect scenes. After changing a parent or Enabled flag, call propagate() so Active and GlobalTransform update, as the engine does at stage boundaries.
  • Events: set ctx.services.events = &[AnyBox(Box::new(Hit { … }))] to simulate last frame's broadcasts, and ctx.services.scene_events for contacts. Read what your system emitted from commands (ComponentCommand::Emit).
  • Services: set ctx.services.physics = Some(&mock) with your own PhysicsQuery to fake raycasts (the Laser test does this), nav, screen and net likewise.
  • Actions: call component.invoke_action(&mut ActionCtx { … }, "Open", &[]) directly.
  • Multi-frame behaviour: call run in a loop and assert after each step; commands queued by one frame are not applied by the harness, so assert on them instead.

src/main.rs is short and yours to edit:

use anyhow::Result;

fn main() -> Result<()> {
    zestengine_engine::init_logging();

    // A shipped build carries assets.pak next to the executable; during `cargo run`
    // the assets live in the project folder.
    let exe_assets = std::env::current_exe()
        .ok()
        .and_then(|p| p.parent().map(|d| d.join("assets")))
        .filter(|p| p.join("project.zestengine").is_file());
    let assets_root = exe_assets.unwrap_or_else(|| std::path::PathBuf::from(env!("CARGO_MANIFEST_DIR")));

    let config = zestengine_engine::GameConfig::from_project_dir(assets_root)?;
    zestengine_engine::run_game(config, |registry| {
        zestengine_project_components::zestengine_register(registry);
    })
}
  • GameConfig::from_project_dir reads project.zestengine: the starting scene (Project Settings → Starting scene), window title, control bindings, physics, audio and rendering settings. Build a GameConfig by hand (GameConfig { boot_scene: "scenes/main.scene".into(), width: 1280.0, height: 720.0, ..Default::default() }) when you want full control; every field has a default.
  • run_game(config, register) opens the window, loads the boot scene and runs the frame loop until the window closes. register receives the ComponentRegistry after the built-in components are added: this is where your project's components, systems and entities are registered (see Plugins in a project).
  • Editor Play mode and a shipped game run the same loop. File → Build Game (or zestengine --build) produces a standalone executable with an assets.pak next to it.

How your code is called

You do not write a main loop. You register systems, and every frame the engine runs them stage by stage (see Stages). A system receives:

Immediate and queued

Every operation in this guide is one of two kinds, and the tables below say which:

  • Immediate: reads, and writes that edit component data in place (host.edit::<T>(..), host.set_translation(..)). The change is visible to every system that runs later in the same stage.
  • Queued: anything that pushes a ComponentCommand (spawn, destroy, impulses, scene loads, sounds, saves, network). The engine applies queued commands, in order, when the stage finishes. Spawn calls return the new ObjectId right away, but the object exists only once the stage ends.

Targets

Methods that act on another object take impl Into<ObjectRef>: an ObjectRef field from your component, or a plain ObjectId. An unset, deleted or hidden target is not an error: reads return None, writes return false or do nothing.

Read a position, change it, write it back. Writing a world position to a parented object's local translation is the classic mistake; set_world_position converts through the parent chain for you:

fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
    let direction = host.input.axis2("Move");
    let step = Vec3::new(direction.x, 0.0, -direction.y) * self.speed * host.dt;
    let position = host.translation() + step;
    host.set_translation(position);
}

Transform itself has forward() (local −Z in world space), right(), up() and matrix().

Frame-rate independent motion. Multiply speeds by host.dt. To ease toward a target, close a share of the gap each frame with 1 − e^(−k·dt), which gives the same result at any frame rate (see the smooth follow recipe):

let blend = 1.0 - (-sharpness * host.dt).exp();
host.set_world_position(here.lerp(wanted, blend));

Moving physical things. A character with a Character component moves with move_character(delta) (it slides along walls and climbs steps; gravity is yours to apply, and host.grounded() says whether it touched the ground). Rigid bodies move through forces and impulses (see Physics). Writing the transform of a dynamic or fixed body teleports it to that pose; a kinematic body follows its transform every physics step (and pushes the dynamic bodies it meets), which is how platforms and doors are moved from code.

The translation(), set_translation(), world_position() and similar methods come from the MoveHost trait: use zestengine_core::MoveHost;.

The camera is an object with a Camera component; host.set_active_camera(target) makes it the one that renders.

Contacts (collisions and trigger overlaps) are not polled: they arrive as scene events in the Events stage. See Scene events.

Components can be restricted to one side with TypedComponent::NET_ROLE (a Server component is stripped from players, a Client one from a dedicated server). Session commands (NetHost, NetJoin, NetDisconnect, NetKick, …) are applied by the host application, not the play session, which is why they are queued like every other command.

Things that surprise people.

  • has_authority(id) is true offline, but on a client it is false for any object with no recorded owner, including ordinary non-networked scene objects (an unowned object belongs to the host). Guard local-only objects with driven_remotely() instead, which checks that the object is actually networked.
  • i_am_host() is false offline (it needs a session); has_authority is true. They answer different questions.
  • A synced variable another peer wrote is announced as an event at the start of the frame, but the component is updated at the end of it: in the frame you see the change, net_var(..) still returns the old value.
  • The host cannot net_despawn an object a client owns (it fails the authority check): take the object with transfer_ownership first, or have the owner despawn it.
  • A self-initiated net_disconnect() does not deliver a Disconnected event to your own systems.
  • NetValue has no 64-bit float: send a time or large number as Bytes (or two ints) to keep precision.

Lag compensation. For hit checks on a server, host.ray_cast_rewound(shooter, origin, dir, max_dist) casts against where the targets were when the shooter fired, and ray_cast_at(time, …) against any recent moment (net_time() is the current simulation time). The rewind window is the session's configured maximum (default 0.25 s, hard cap 0.9 s).

Recipes

Smooth follow camera

Run in LateUpdate, after the target has moved this frame.

#[derive(Serialize, Deserialize)]
pub struct SmoothFollow {
    pub target: ObjectRef,
    pub offset: [f32; 3],
    pub sharpness: f32,
}

impl SmoothFollow {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        let Some(goal) = host.position_of(self.target) else { return };
        let wanted = goal + Vec3::from(self.offset);
        let here = host.world_position();
        // 1 - e^(-k·dt) is the share of the gap to close this frame: the result is
        // the same whether the game runs at 30 or 240 frames per second.
        let blend = 1.0 - (-self.sharpness * host.dt).exp();
        host.set_world_position(here.lerp(wanted, blend));
    }
}

registry.register_system_for::<SmoothFollow>("game::smooth_follow", Stage::LateUpdate, |world, ctx| {
    run_ordered(world, ctx, SmoothFollow::update)
});

WASM Scripting

ZestEngine runs sandboxed WebAssembly (WASM) modules inside the game process. A module can expose named actions and readable properties that show up in the editor's event-binding dropdowns, react to every frame, emit events, and call other components' actions, all without being able to touch anything the engine did not hand it.

This guide covers writing a module, building it, attaching it to an object, binding its functions to events, and shipping it in a project, a content package or a mod.

Overview

Why WASM

ZestEngine is Rust-first. Gameplay that ships with your game is native Rust: ECS components linked into the game binary, with the full engine API and no sandbox (see ECS.md and ENGINE_API.md). That is the trusted path, and it is the right one for your own game code.

It cannot be the path for code you do not trust. A player-made world, a prop from a content package or a mod must not be able to run machine code in your process. WASM is the engine's only sandbox for that: a module runs inside wasmtime and can only call the functions the engine imports into it, each call bounded by an instruction budget, a memory cap and a stack cap. There is no WASI, no network, no filesystem, no wall clock and no randomness.

The same mechanism also works for trusted project modules, for example logic you want to write in another language.

The Wasm Script component

WASM modules run through the Wasm Script component (WasmScript, source crates/zestengine-core/src/wasm/). A module imports from the module host and exports zest_invoke, zest_read_property and an optional zest_update. It declares its actions, properties and capabilities in a zest_manifest custom section, so they show up in the editor's binding dropdowns next to the built-in components. Its state lives in its own linear memory (it is not saved with the scene), it hot-reloads when its file changes (polled every 0.5 s), and content packages and mods accept it. Each entry-point call gets 5 M units of fuel for a project module and 1 M for an untrusted one.

Quick start

This takes the repository's guest/example-counter crate from source to a working counter bound to a button. The build steps (1 to 3) were not run end to end when this guide was written; see the note at the top of Toolchain and building.

1. Install the WASM target (once).

rustup target add wasm32-unknown-unknown

2. Build the example.

cd guest/example-counter
cargo build --release --target wasm32-unknown-unknown

The module is guest/example-counter/target/wasm32-unknown-unknown/release/example_counter.wasm. The guest crates are their own Cargo workspaces, so target/ is inside the crate folder.

3. Put it in your project.

mkdir -p /path/to/my-project/logic
cp target/wasm32-unknown-unknown/release/example_counter.wasm /path/to/my-project/logic/counter.wasm

Use a folder other than src/, target/, plugins/ or build*: the build pipeline does not treat those as asset folders.

4. Add the component. In the editor, select (or create) an object, click Add Component at the bottom of the inspector and pick Wasm Script. Set Module to logic/counter.wasm with the asset picker or by dragging the file onto the field. The inspector now shows what the module declared:

Counter
Add(amount: Int)
Reset()
property count: Int
capabilities: events

If the module is rejected, the inspector shows the reason in red instead (see Testing and debugging).

5. Bind an action. On another object add an Interactable component. Under On interact click Add action, then set Target to the counter object, Component to Wasm Script, Function to Add to count, and the amount (Int) parameter to the Value 5.

6. Try it. Enter Play mode. The row's play button (Test: run this action now) fires the binding immediately, or interact with the object normally. To see the number, add a UI Text whose SetText action takes its text from a Property source: object = the counter, component = Wasm Script, property = count.

7. Iterate. Rebuild and copy the file again. The engine notices the changed file within about half a second and loads a fresh instance (the counter restarts at 0). The inspector's Reload module button forces it.

Release profile and size

example-counter ships this profile:

[profile.release]
opt-level = "s"
lto = true
panic = "abort"

panic = "abort" removes the unwinding machinery. lto = true lets the linker drop unused code. opt-level = "s" trades a little speed for size. Beyond that, the usual size costs are float formatting, format!-heavy error messages and large dependencies. Keep modules small: the file cap is 4 MiB for project modules and 1 MiB for packages and mods (512 KiB for Prop packages). opt-level = "z" and codegen-units = 1 are standard Rust size options but were not tried here.

Do not strip custom sections. The engine needs the zest_manifest section; a tool that removes custom sections (some strip options and optimisers do) makes the module fail with no "zest_manifest" custom section. After any post-processing, check that the module still loads. grep -c -a zest_manifest module.wasm is a quick sanity check.

Where the engine looks for the module

The module field of a Wasm Script is one of:

  • a path relative to the process working directory (the editor sets it to the project root), for example logic/door.wasm;
  • an absolute path;
  • an @<id> asset reference. The editor's asset picker stores this form: it writes a .meta sidecar next to the .wasm (keep it under version control) so renaming or moving the file keeps the reference valid.

A built game ships every file reachable from its scenes, so a module named by a Wasm Script component is included. A module loaded some other way is included only if it sits under resources/ or its path appears as a string literal in src/.

The file is polled for changes (modification time and size) about every 0.5 s. Editing the module field also loads a fresh instance. Each component gets its own instance with its own memory, even when several objects use the same .wasm; the compiled code and the manifest tables are shared.

Content packages and mods

Packages (.zestenginepak) carry .wasm files under files/<project-relative path>. The builder (Tools > Build Content Package) and the extractor both validate each module without running it, so a bad module fails the build instead of a player's game. On extraction, strings in RON files that name packaged files, including a Wasm Script's module, are rewritten to absolute paths inside the extraction folder, and that folder is registered as untrusted. A module's trust is its location. See Limits and safety.

Mods reuse the same archives. The mod mounts into a per-session snapshot, module references resolve inside it, and the module's trust and action permissions come from the mod. A mod can also replace a game's own .wasm by path; the replacement keeps the mod sandbox. See Limits and safety, and the game's mod settings under Project Settings > Mods in the editor.

Writing modules in other languages

Anything that produces a core WebAssembly module with the right shape works. The engine only looks at the binary:

  1. Imports, if any, come from the module host and name functions in Host imports. No WASI, no other namespace, no imported memory, table or global.
  2. One exported 32-bit, non-shared memory named memory, whose initial size is within the page cap.
  3. Exactly one custom section named zest_manifest containing UTF-8 RON, at most 64 KiB.
  4. The exports the manifest implies: zest_alloc and zest_invoke when it declares actions, zest_read_property when it declares properties. zest_update and zest_last_error are optional.
  5. Every capability a host import needs is declared in the manifest.

This is a complete module in WAT. It was assembled with the wat crate and loaded by the engine's loader; it also passes the package validator's untrusted limits:

(module
  (@custom "zest_manifest" "(name: \"Flag\", actions: [(name: \"Raise\", ugc_safe: true)], properties: [(name: \"raised\", ty: Bool)])")
  (memory (export "memory") 1)
  (global $raised (mut i32) (i32.const 0))

  ;; Scratch buffer the host writes the argument block into.
  (func (export "zest_alloc") (param $len i32) (result i32)
    i32.const 1024)

  ;; Action 0 is Raise. Status 0 means success, anything else is a failure.
  (func (export "zest_invoke") (param $action i32) (param $ptr i32) (param $len i32) (result i32)
    (if (i32.eqz (local.get $action))
      (then (global.set $raised (i32.const 1)) (return (i32.const 0))))
    i32.const 1)

  ;; Property 0 is raised, encoded as one Bool value: tag 0, then one byte.
  (func (export "zest_read_property") (param $index i32) (result i64)
    (i32.store8 (i32.const 4096) (i32.const 0))
    (i32.store8 (i32.const 4097) (global.get $raised))
    ;; (len << 32) | ptr, with len = 2 and ptr = 4096
    (i64.or (i64.shl (i64.const 2) (i64.const 32)) (i64.const 4096))))

Other toolchains (C or C++ with clang, Zig, AssemblyScript, a post-link step that appends the section) should work if they produce the shape above, but none was tried for this guide. The one non-obvious part is embedding the custom section; zest-guest does it with #[unsafe(link_section = "zest_manifest")] on a static.

The WasmScript component ABI

This is the exact contract between the engine and a Wasm Script module. guest/zest-guest implements all of it for Rust authors. All numbers below are copied from crates/zestengine-core/src/wasm/{abi,sandbox,component}.rs.

Manifest

A custom section named zest_manifest holds RON text, at most 64 KiB (65536 bytes). It is read without running any guest code, which is why packages and tools can inspect a module cheaply.

(
    name: "Door",                         // shown in the inspector
    api: 1,                               // manifest version; 1 is the only one
    capabilities: ["events", "invoke"],   // host imports the module uses
    actions: [
        (name: "Open", label: "Open door", ugc_safe: false, params: [
            (name: "blocker", ty: Object),
            (name: "sound", ty: String, default: Some(String("audio/door_open.wav"))),
            (name: "offset", ty: Vec3, default: Some(Vec3((0.0, 1.0, 0.0)))),
        ]),
    ],
    properties: [(name: "is_open", ty: Bool)],
)
FieldTypeMeaning
namestringInspector title. Empty shows as (unnamed).
apiu32Manifest version. Must be 1 or less (default 0 is accepted); write 1.
capabilitieslist of stringsAny of state, events, read, invoke. Unknown names fail the load.
actionslistAt most 64. The position in the list is the action_index passed to zest_invoke.
actions[].namestringWhat bindings store in scenes. Never rename a shipped action.
actions[].labelstringDropdown text; defaults to name.
actions[].paramslistAt most 16, in the order the guest receives them.

Names are 1 to 64 bytes of letters, digits, space, _, - and ., and action names and property names must each be unique. Notes from testing the real parser:

  • A Vec3 default is written with a tuple: Vec3((0.0, 1.0, 0.0)). Square brackets fail with Expected opening '('.
  • Unknown fields are ignored, not rejected. A typo such as ugc_save: true silently leaves the action not UGC-safe.
  • Indices can change freely between builds; names are the stable identity. Keep your action numbers in constants next to the manifest.
  • The engine builds its dropdown tables once per distinct manifest text and keeps them for the life of the process, at most 512 distinct manifests, after which loading fails until restart.

Value encoding

All integers are little-endian. A value is a one-byte tag followed by a payload.

TagTypePayload
0Bool1 byte, 0 or 1 (any non-zero byte reads as true)
1Inti64, 8 bytes
2Floatf32, 4 bytes
3Stringu32 byte length (at most 16384), then UTF-8 bytes
4Vec33 x f32, 12 bytes
5Objectu128 object id, 16 bytes; all zero means none

An argument block is a u32 count (at most 32) followed by that many values, in parameter order, at most 64 KiB in all. The host has already coerced every argument to the declared parameter type and filled in defaults for missing ones, so a guest can decode by position without checking tags. Coercion is the engine's usual one: numbers and bools convert between each other (an Int from a Float rounds), any value converts to text, everything else must match.

Property values are a single tagged value (no count). The host coerces the result to the declared property type; a value that cannot be coerced reads as "no value".

Guest exports

ExportSignatureRequiredBehaviour
memorymemoryYesExactly one, 32-bit, not shared.
zest_alloc(len: i32) -> i32When actions are declaredReturn a pointer to at least len writable bytes. The host copies the argument block there before each zest_invoke. Returning the same scratch buffer every time is fine.
zest_invoke(action_index: i32, args_ptr: i32, args_len: i32) -> i32When actions are declaredRun an action. Return 0 for success; any other value is a failure reported to the binding.
zest_last_error() -> i64NoAfter a non-zero status, return (len << 32) | ptr of a UTF-8 message (cut to 512 bytes). Without it the error is returned status N.
zest_read_property(index: i32) -> i64When properties are declaredReturn (len << 32) | ptr of one encoded value in guest memory, valid until the next call, or 0 for "no value".
zest_update(dt: f32)NoOnce per frame while playing, for active objects.

Exports are looked up by name and signature. If zest_invoke, zest_alloc or zest_read_property is declared but has the wrong signature, the load fails. A zest_update or zest_last_error with the wrong signature is silently ignored, so "my update never runs" usually means a wrong signature (it must be (f32) -> ()).

Host imports

A module may import only these, all from the module host. Pointers are i32 offsets into the guest's memory. Strings are UTF-8 (ptr, len) pairs, at most 256 bytes (except log, which cuts at 512).

ImportWasm signatureCapabilitySemantics
log(ptr, len)noneWrite a line to the engine log (INFO, target wasm). At most 32 lines per entry-point call; text beyond 512 bytes is cut; invalid UTF-8 is replaced.
get_dt() -> f32noneFrame time passed to the most recent zest_update (the engine caps one frame at 0.25 s before applying the time scale). It is 0.0 until the first update, and inside zest_invoke it is the value from the last update, not a fresh one.
get_time() -> f32noneGame time at the most recent zest_update; same caveat. The only clock.
get_self(out_ptr)noneWrite the owner object's 16-byte id to out_ptr.

get_float(ptr, len) -> f32stateRead a named float from this component's store; 0.0 if unset.

get_float and set_float are a small host-side store keyed by name. It is not saved, not replicated and not visible to bindings (only to tests through WasmScript::float), and it dies with the instance. Your own linear memory persists across calls just as well, so you rarely need it.

get_property details:

  • obj_ptr points at a 16-byte object id; all zero means this object.
  • comp_len of 0, or the component Object, reads the built-in object properties name (String), active (Bool) and position (Vec3).
  • The first instance of the component on that object is read.
  • On success the encoded value is written to out_ptr and its length is returned (always more than 0). Negative returns are in the table below.
  • It works inside zest_update, and inside zest_invoke when the engine passes a world view (always in Play). Inside zest_read_property, and in a test with no world view, it returns -2.
  • Inside zest_invoke and zest_update the module's own component is not readable; its sibling components and other objects are. Sibling Wasm Script components on the same object are readable by their declared property names.

invoke details:

  • The call runs after your function returns, when the owning component next drains its queue (the next gameplay pass). It never runs inside the guest call, so there is no return value from the target action.
  • It goes through the same resolution and type checks as an editor binding: the object must exist, have a component of that name, which must declare that action, and the arguments are coerced to the declared parameter types. Problems after queueing are logged by the engine, not returned to you.
  • obj_ptr all zero means this object. For built-in object actions (SetActive, ToggleActive, PlaySound, EmitEvent, LoadScene) use the component name Object.
  • The argument block is the encoding above, at most 64 KiB.
  • At most 16 calls can be waiting in the queue.

Errors and traps

There are three outcomes.

  • Load error. The file is missing, not a valid module, fails validation or instantiation. The component stays inert and shows the message in the inspector, and one ERROR line is logged. Fixing the file (or the module field) loads it again.
  • Guest failure. zest_invoke returns a non-zero status. This is the module saying no; it does not disable anything. The message from zest_last_error (or returned status N) goes back to the binding, which logs it as a warning such as action Wasm Script.Open: <message>. The rest of a binding batch still runs. (The editor's Test button reports only problems resolving the binding, such as a missing action; a guest failure shows up in the log.)
  • Trap. Running out of fuel, a stack overflow, unreachable (this includes every Rust panic with panic = "abort"), an out-of-bounds access, or a host call that rejects its arguments. The instance is dropped, one ERROR line is logged, and the component stays disabled (later calls do nothing, and bindings to it still resolve) until its module changes: an edited file, a changed module field or the inspector's Reload module button.

There is no rollback. The guest's memory goes away with the instance. Events a failed or trapping action already emitted are still delivered; events and queued calls from a trapping zest_update are discarded. A malformed zest_read_property result (wrong length, unknown tag) is not a trap: it is logged as Wasm Script property '<name>': <reason> and the property reads as no value.

Guidelines that follow from the ABI:

  • Match the manifest and the code. The host always passes every declared parameter, so args[i] is safe when the code agrees with the manifest. A mismatch panics, and a panic traps.
  • Use the as_* helper that matches the declared type: the host has already converted the argument to that type, so the helper is exact. (The helpers' own conversions differ from the host's, for example as_i64 truncates a float where the host rounds.)
  • Return Err(message) for expected problems (bad input, wrong state). Reserve panics for bugs.
  • State lives in your Module struct. It survives between calls, resets on hot reload, and is not saved with the scene.

The counter example

guest/example-counter/src/lib.rs, minus its doc comment. It is the smallest useful module: two actions, one property and one event.

use zest_guest::{Module, Value};

zest_guest::manifest!(
    r#"(
    name: "Counter",
    api: 1,
    capabilities: ["events"],

#[derive(Default)]

            1 => self.0 = 0,

        }

A door that opens through an action

A door that plays a sound, switches off a blocking collider and reports its state. It uses invoke to call the built-in Object.PlaySound and Object.SetActive actions, so it declares the invoke capability and works as a project module, or as a mod whose game allow-lists those two actions (packages cannot use invoke). Checked with cargo check on the host target; not built for wasm32.

use zest_guest::{Module, ObjectId, Value};

zest_guest::manifest!(
    r#"(
    name: "Door",
    api: 1,
    capabilities: ["events", "invoke"],
    actions: [
        (name: "Open", label: "Open door", params: [
            (name: "blocker", ty: Object),
            (name: "sound", ty: String, default: Some(String("audio/door_open.wav"))),
        ]),
        (name: "Close", label: "Close door", params: [
            (name: "blocker", ty: Object),
        ]),
        (name: "Toggle", label: "Toggle door", params: [
            (name: "blocker", ty: Object),
            (name: "sound", ty: String, default: Some(String("audio/door_open.wav"))),
        ]),
    ],
    properties: [(name: "is_open", ty: Bool)],
)"#
);

const OPEN: u32 = 0;
const CLOSE: u32 = 1;
const TOGGLE: u32 = 2;

/// The all-zero id: "no object" in a parameter, "this object" in a host call.
const NONE: ObjectId = [0; 16];

#[derive(Default)]
struct Door {
    open: bool,
}

fn object(v: &Value) -> ObjectId {
    match v {
        Value::Object(id) => *id,
        _ => NONE,
    }
}

impl Door {
    fn set_open(&mut self, open: bool, blocker: ObjectId, sound: &str) -> Result<(), String> {
        if self.open == open {
            return Ok(()); // already there, nothing to do
        }
        // The blocker is a collider that is active while the door is shut. An
        // unset parameter would mean "this object" to the host, so skip it.
        if blocker != NONE {
            let status = zest_guest::invoke(blocker, "Object", "SetActive", &[Value::Bool(!open)]);
            if status != 0 {
                return Err(format!("could not queue SetActive (status {status})"));
            }
        }
        if open && !sound.is_empty() {
            zest_guest::invoke(NONE, "Object", "PlaySound", &[Value::Str(sound.to_owned()), Value::Float(1.0)]);
        }
        self.open = open;
        zest_guest::emit_event(if open { "DoorOpened" } else { "DoorClosed" });
        zest_guest::log(if open { "door opened" } else { "door closed" });
        Ok(())
    }
}

impl Module for Door {
    fn invoke(&mut self, action: u32, args: &[Value]) -> Result<(), String> {
        match action {
            OPEN => self.set_open(true, object(&args[0]), args[1].as_str()),
            CLOSE => self.set_open(false, object(&args[0]), ""),
            TOGGLE => self.set_open(!self.open, object(&args[0]), args[1].as_str()),
            _ => Err(format!("no action {action}")),
        }
    }

    fn property(&mut self, index: u32) -> Option<Value> {
        (index == 0).then(|| Value::Bool(self.open))
    }
}

zest_guest::export!(Door::default());

To wire it up, put the module on the door object, create the blocker as a child collider, and on an Interactable add an On interact action: Target = the door, Component = Wasm Script, Function = Toggle door, blocker = the blocker object, sound = a sound in your project. Other objects can read is_open through a Property source.

Calling a built-in action

Hazard.Zap damages whatever is passed to it. It reads Health.dead first (capability read) and queues Health.Damage (capability invoke). Health.Damage is not ugc_safe, so this is a project module, or a mod whose game lists Health.Damage in its allow-list. Checked with cargo check on the host target; not built for wasm32.

use zest_guest::{Module, ObjectId, Value};

zest_guest::manifest!(
    r#"(
    name: "Hazard",
    api: 1,
    capabilities: ["read", "invoke"],
    actions: [
        (name: "Zap", label: "Damage target", params: [
            (name: "target", ty: Object),
            (name: "amount", ty: Float, default: Some(Float(10.0))),
        ]),
    ],
    properties: [(name: "zaps", ty: Int)],
)"#
);

#[derive(Default)]
struct Hazard {
    zaps: i64,
}

impl Module for Hazard {
    fn invoke(&mut self, action: u32, args: &[Value]) -> Result<(), String> {
        if action != 0 {
            return Err(format!("no action {action}"));
        }
        let target: ObjectId = match &args[0] {
            Value::Object(id) => *id,
            _ => [0; 16],
        };
        if target == [0; 16] {
            return Err("Zap needs a target".into());
        }
        let amount = args[1].as_f32();
        if amount <= 0.0 {
            return Err("amount must be positive".into());
        }
        // `read` capability: skip the call when the target is already dead.
        if let Some(Value::Bool(true)) = zest_guest::get_property(target, "Health", "dead") {
            return Ok(());
        }
        // `invoke` capability: queue Health.Damage(amount) on the target.
        let status = zest_guest::invoke(target, "Health", "Damage", &[Value::Float(amount)]);
        if status != 0 {
            return Err(format!("Health.Damage was not queued (status {status})"));
        }
        self.zaps += 1;
        Ok(())
    }

    fn property(&mut self, index: u32) -> Option<Value> {
        (index == 0).then(|| Value::Int(self.zaps))
    }
}

zest_guest::export!(Hazard::default());

Put it on a hazard volume that also has Trigger Events. In On enter add an action: Target = the volume, Component = Wasm Script, Function = Damage target, target from an Event source with field other (the object that entered), amount = a Value.

How the permission checks work for this call:

  1. The manifest must declare invoke, and the module must be allowed it: project modules are, packages never are, mods are only for calls on the game's allow-list.
  2. The call is queued and then resolved like any binding. If the target has no Health component, or Damage is misspelled, the engine logs target has no Health component or Health has no action 'Damage' and nothing happens. Your invoke still returned 0, because it only queued.
  3. For mods, the call is dropped with a warning Mod script denied action Health.Damage unless Health.Damage is on the game's allow-list. The check compares the exact text you passed, so use Object (not an empty string) for built-in object actions.
  4. ugc_safe on the target action is not checked on this path. It controls who may bind an action, not who may queue it.

Per-frame logic and events

Ticker shows update and events: it counts time and emits a Tick event at an interval. It must be exported with export!(init, update). Checked with cargo check on the host target; not built for wasm32.

use zest_guest::{Module, Value};

zest_guest::manifest!(
    r#"(
    name: "Ticker",
    api: 1,
    capabilities: ["events"],
    actions: [
        (name: "SetInterval", label: "Set tick interval", ugc_safe: true, params: [
            (name: "seconds", ty: Float, default: Some(Float(1.0))),
        ]),
    ],
    properties: [(name: "ticks", ty: Int)],
)"#
);

struct Ticker {
    interval: f32,
    since_tick: f32,
    ticks: i64,
}

impl Default for Ticker {
    fn default() -> Self {
        Self { interval: 1.0, since_tick: 0.0, ticks: 0 }
    }
}

impl Module for Ticker {
    fn invoke(&mut self, action: u32, args: &[Value]) -> Result<(), String> {
        match action {
            0 => {
                let seconds = args[0].as_f32();
                if seconds < 0.05 {
                    return Err(format!("interval {seconds} is too short (minimum 0.05)"));
                }
                self.interval = seconds;
                Ok(())
            }
            _ => Err(format!("no action {action}")),
        }
    }

    fn property(&mut self, index: u32) -> Option<Value> {
        (index == 0).then(|| Value::Int(self.ticks))
    }

    fn update(&mut self, dt: f32) {
        self.since_tick += dt;
        while self.since_tick >= self.interval {
            self.since_tick -= self.interval;
            self.ticks += 1;
            zest_guest::emit_event("Tick");
        }
    }
}

zest_guest::export!(Ticker::default(), update);

The 0.05 s minimum keeps the loop under the 16 events per call cap for frames up to 0.8 s long (after time scaling); extra events are silently dropped.

Events

A module can emit events but cannot receive them: there is no import that delivers events to a guest. emit_event(name) (capability events) broadcasts an ActionEvent { name, source, instigator } on the engine's event bus: source is the object the module sits on, and instigator is who triggered the action (always none from zest_update). Events from an action call are delivered right after it; events from zest_update after the update. Native Rust gameplay reads them on the next frame, for example (a sketch; see ECS.md for the system signatures):

for event in ctx.events::<ActionEvent>() {
    if event.name == "DoorOpened" {
        // event.source is the door's object id
    }
}

As of this writing no built-in component reacts to a named event from the editor. To react inside a module, expose an action and have a binding call it, or poll another component's property from zest_update with get_property.

Panics and the engine log

With panic = "abort", a panic becomes an unreachable trap and its message is lost (a wasm32-unknown-unknown module has no stderr). Route it to the engine log by installing a hook in the init expression of export!; this variant of the door was checked with cargo check on the host:

zest_guest::export!({
    // Route panic messages to the engine log (the default message is lost on wasm32).
    std::panic::set_hook(Box::new(|info| zest_guest::log(&info.to_string())));
    Door::default()
});

Limits and safety

What a module can and cannot do

A module can compute, keep state in its own memory, read the properties the engine lets it read, emit events and queue actions. It cannot open a file or socket, read a clock other than get_time, get random numbers, load code, or see anything the capabilities do not give it. The import allowlist is checked before instantiation, so an unknown import fails the load rather than failing later. The engine also turns on NaN canonicalisation and turns off relaxed SIMD, so float results do not depend on the CPU.

Fuel is wasmtime's instruction counter: roughly one unit per executed instruction, so it is deterministic and independent of CPU speed. Each entry-point call starts with a full budget: zest_alloc plus zest_invoke share one, zest_read_property and zest_update get their own, and so does instantiation (a start function runs inside it). Running out ends the call with a trap. There is no wall-clock deadline for Wasm Script; the engine has no epoch timer for it. A frame with many scripts can still add up to many full budgets, so keep zest_update cheap.

The stack note: SandboxLimits::untrusted() declares 256 KiB, but the engine configures one stack limit for all modules, the trusted 512 KiB (crates/zestengine-core/src/wasm/sandbox.rs). Do not rely on the smaller number.

Why each limit exists:

  • File size bounds compile time and package size.
  • The memory cap stops a module allocating the host out of RAM. Growth past the cap returns -1 to the guest (Rust's allocator then aborts, which traps).
  • Fuel stops an infinite loop from freezing the frame, since guest code runs synchronously on the game thread.
  • The stack cap turns deep recursion into a trap instead of a host crash.
  • Per-call caps (32 log lines, 16 events, 16 queued calls, 64 float keys, 256-byte strings) keep one call from flooding the host.

Trust by location

The engine does not trust a manifest to say how trusted it is; trust follows where the file is.

  • Anything under a project folder is trusted.
  • Anything under an extracted content package folder is untrusted, with tighter limits. The content manager registers the package's files folder when it extracts it.
  • Anything under a mod's folder in the session snapshot, or a .wasm a mod replaced, is untrusted with the mod rules below.

Untrusted modules cannot declare invoke (the load fails with capabilities not permitted here: invoke), and they can only expose actions whose manifest sets ugc_safe: true, and only when the content kind allows module actions at all (allow_wasm_actions: true for World and Prop, false for Avatar).

ugc_safe

ugc_safe is an opt-in on each action: "binding this from user-generated content is acceptable". Mark an action safe only if it changes nothing outside the module, cannot hurt other players and cannot leave the world. Counting and toggling a flag are safe; dealing damage or loading a scene is not.

How it is enforced today:

  • For Wasm Script actions in untrusted content, the runtime refuses a non-safe action with '<name>' is not allowed for untrusted content (needs ugc_safe and content limits that allow module actions), and hides every action when the content kind disallows module actions.
  • In the editor, when you edit an object that came from a content package or while the Content Builder is open, the action dropdowns offer only ugc_safe actions, and an existing binding to any other action is flagged Not allowed in user-generated content. This applies to built-in actions too, such as Health.Damage.
  • For built-in actions, as of this writing no runtime or load-time check rejects a package scene's binding to an action that is not ugc_safe. For those, treat the editor filter as authoring help, not as a security boundary.

Mod permissions and the action allow-list

A mod's modules get the untrusted limits but are allowed the invoke capability, because a game may want mods to do things like deal damage. The game decides which actions:

  • In Project Settings > Mods the game lists exact Component.Action names in the allow-list (mods.actions in project.zestengine), for example Health.Damage.
  • A mod's own manifest (actions) lists the ones it needs. The mod is refused when the profile is validated or mounted if the game has not exposed one of them.
  • At run time every queued invoke is checked against the mod's list: a call whose Component.Action is not on it is dropped with a warning Mod script denied action Component.Action.
  • A mod cannot grant itself anything: the game's list (Project Settings > Mods) is the ceiling.

Further mod rules in the code: a mod module cannot be hot reloaded (it runs from the session snapshot); a mod's Wasm Script components are assigned the Server network role; and on a connected client a mod module's zest_update does not run. A mod module's own actions still need ugc_safe to be callable from bindings.

Networking and dedicated servers

A Wasm Script has the network role Both by default: it exists and runs on every peer, including a dedicated server, and each peer has its own instance. Its state is not replicated, and it is not saved with the scene. Choose where it runs from the component's options menu (Network Role: Both, Client or Server), or project-wide in Project Settings > Network roles. The dedicated-server build keeps .wasm files.

For gameplay that must be authoritative, give the module the Server role and put the outcome into the engine's replication tools, for example Network Variables or a spawned network object (see the networking components in the ECS Guide and the Network Variables and RPC calls in the Engine API Guide). Module state is not shared between peers, so two peers running the same module will not stay in sync by themselves.

Using WASM from the editor and from scenes

Adding the component

Select an object, click Add Component and choose Wasm Script. The inspector shows:

  • Module: an asset field for .wasm files (drag one from the file browser, or browse). It stores an @<id> reference.
  • The module's name from its manifest, or a red error message if loading failed. A note appears when the module comes from untrusted content.
  • One line per declared action, Name(param: Type, ...), with (not UGC-safe) on actions without the flag, then property name: Type lines and the capability list.
  • Reload module, which re-reads the file and replaces the instance. Opening the inspector also re-checks the file, so a rebuild shows up while it is open.

You can add several Wasm Script components to one object, each with its own module.

Binding actions

The action editor appears on Interactable (On interact, When turned on, When turned off, On press, On release), Trigger Events (On enter, On exit), UI Button (On click: call) and Animation Event Bindings (Runs, one list per named event). Each row has:

  • Target: which object (empty means the object that owns the event source).
  • Component: Object (the built-in object actions) or a component on the target. Components with several instances are numbered, for example Wasm Script #2 (door).
  • Function: the action's label.
  • One row per parameter, each with a source: Value (a constant), Property (a property of any component on any object, including a Wasm Script property), Instigator (a property of whoever triggered the event) or Event (a field of the event: Interactable offers instigator, object, uses, on; Trigger Events offers other, object; animation events offer name, object).
  • A Test button (Play mode only) that fires the row as if the event had happened and shows Fired or the resolve error under the row (a failure inside the module is only logged), and buttons to reorder or remove the row. Warnings appear under a row when a source does not resolve or its type cannot convert to the parameter's type.

Missing arguments use the manifest defaults. Types convert as described in Value encoding. A binding that cannot resolve (target gone, action missing) logs once and does nothing.

In a scene file the binding is plain RON inside the source component's data, for example (copied from a serialised Interactable, abbreviated):

on_interact:[
  (target:(Some("37daca0c-5c38-460b-8d74-840effdf98fa")),component:"Wasm Script",action:"Add",args:[Const(Int(5))],instance:0,instance_label:""),
  (target:(Some("37daca0c-5c38-460b-8d74-840effdf98fa")),component:"Wasm Script",action:"Add",args:[Instigator(component:"Health",property:"current")],instance:1,instance_label:"counter"),
]

Scenes store names only (component, action), never action indices, so reordering actions in a module does not break existing bindings.

Instance labels

When an object has several components of one type, a binding stores the position among them (instance) and a label (instance_label). For a Wasm Script the label is the module's file name without folders or extension (door for scripts/door.wasm). When resolving, a matching label wins over the position, so a binding keeps following its module when you reorder or remove components.

The label is empty when the module field holds an @<id> reference, which is what the editor's asset picker stores. Bindings to such components follow the position only. If you rely on labels, write the plain path in the scene.

Testing and debugging

Unit-testing guest logic on the host

zest-guest compiles on your development machine with stub host imports: they do nothing and return zero, except get_property and invoke, which report -2. So cargo test in the guest crate works for logic that does not depend on the host. A test added to the end of guest/example-counter/src/lib.rs (ran and passed on the host):

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn add_and_reset() {
        let mut c = Counter::default();

        c.invoke(1, &[]).unwrap();
        assert_eq!(c.property(0), Some(Value::Int(0)));
        assert!(c.invoke(9, &[]).is_err());

}

Testing a module in the real sandbox

The engine's tests exercise modules without a wasm32 toolchain by writing them in WAT and assembling them with the wat crate; helpers are in crates/zestengine-core/src/wasm/fixtures.rs (compiled only in the engine's own test builds, so copy what you need) and the tests in crates/zestengine-core/src/wasm/tests.rs. A build(manifest, body) helper wraps a body in (module (@custom "zest_manifest" "...") ...), and fixtures such as counter, DRIVER (reads Health.current and queues Health.Damage) and UPDATER (logs, stores dt and time) show every host import in use.

You can do the same from your own crate, with zestengine-core and wat as dependencies. This test loads the Flag module from Writing modules in other languages (FLAG_WAT) the way the engine does, once with the package validator's untrusted limits and once as a project module:

use zestengine_core::actions::ArgValue;
use zestengine_core::wasm::sandbox::ALL_CAPS;
use zestengine_core::wasm::{inspect_module, Instance, SandboxLimits, UNTRUSTED_CAPS};
use zestengine_core::ObjectId;

#[test]
fn flag_module_works_and_passes_the_package_validator() {
    let wasm = wat::parse_str(FLAG_WAT).unwrap();
    // What the package builder checks: untrusted limits, no `invoke`.
    inspect_module(&wasm, &SandboxLimits::untrusted(), UNTRUSTED_CAPS).unwrap();
    let (mut inst, info) = Instance::load(&wasm, SandboxLimits::trusted(), ALL_CAPS, "flag").unwrap();
    assert_eq!(info.manifest.name, "Flag");
    assert_eq!(inst.call_read_property(0).unwrap(), Some(ArgValue::Bool(false)));
    inst.call_invoke(0, &[], ObjectId::NIL, None, None).unwrap();
    assert_eq!(inst.call_read_property(0).unwrap(), Some(ArgValue::Bool(true)));
}

To test a built module, read it from disk instead (std::fs::read("logic/counter.wasm")): the calls are the same, call_update(dt, time, None, ObjectId::NIL) runs zest_update, and inst.float("key") reads the state store.

User-generated content (.zestenginepak)

Players and creators can bring worlds, avatars and props into a running zestengine game without recompiling it, the way VRChat loads worlds and avatars built in Unity. A creator builds a package in the editor (Tools > Build Content Package); the game loads it from a file or URL at runtime.

Why this works without recompiling

A zestengine game is already split into data and code:

  • Scenes, materials, models, textures, audio, animation clips/controllers, baked lighting and custom shader sources are all data files.
  • Behaviour comes from components. A component on an object is just a type name plus serde (RON) data; the logic is compiled Rust that the game links statically (run_game(config, |registry| ...)).

So a package only has to carry the data. Every built-in component (lights, colliders, rigid bodies, joints, animators, audio sources, particles, UI, portals, nav agents, pawns, ...) already exists in every game, which covers a lot of behaviour. Components from a project's plugins only exist in games that link that plugin; the builder flags them and the loader drops any component the running game doesn't have, with a warning.

Sandboxed WASM components can ship custom logic (see "WASM component modules" below). For session-wide asset overrides, scene additions and matching multiplayer mod profiles, see Game mods.

A .zestenginepak is a zip archive (the zip crate was already in the dependency tree; entries are deflated except already-compressed images/audio):

All three kinds use a .scene as the entry. A world is the scene itself (with its <scene>.lightmap/.lightdata/.occlusion/.reflprobe/.audiobake sidecars); an avatar or prop is its object hierarchy saved as a one-root scene. That keeps a single loader path for everything.

Material textures travel twice: the source image (for anything that decodes it) and the BC7/BC6H import-cache blob, so a game loads them without the decode + block-compress step. Blobs are re-bound to the extracted file and skipped on GPUs without BC support (the source is re-encoded instead).

Custom shaders travel as .frag source and are compiled by the game when the content loads (glslc, like the editor). A game without glslc falls back to the standard shader for those materials.

Building (editor)

Tools > Build Content Package opens the build window:

  • World: packages the open scene. Save it first so its baked sidecars sit next to it.
  • Avatar / Prop: packages the selected object and its children. The root is moved to the origin.

Analyse shows what would be written (files, size, triangles, texture memory, components, warnings, errors); Build writes build/content/<name>.zestenginepak (or the chosen output path).

The builder (zestengine_assets::package::plan_package):

  1. Classifies each component: engine built-in (kept), plugin (kept with a warning, or stripped by option), unknown (stripped).
  2. Serializes the entry scene and collects its dependencies transitively by scanning every string in the RON (including strings nested inside component data) for project files, then the files those reference: materials -> textures and shaders, scenes -> models and bake sidecars, models -> .meta import settings, .lmuv markers, glTF buffers/images and FBX textures. Only whitelisted file types are packed (no binaries, no precompiled .spv).
  3. Rejects shader sources that use #include.
  4. Measures triangles (per placement), texture memory and object count and checks them against the kind's limits.
  5. Avatars must have exactly one root; a missing Avatar Descriptor is added with defaults, and the skeleton is checked for a humanoid mapping.

Avatar Descriptor

The Avatar Descriptor component marks an avatar root:

  • view_position: eye point relative to the root (y = eye height). When the avatar is worn, the player's camera child moves here.
  • bone_map: humanoid role -> joint name overrides for rigs the automatic mapper doesn't recognise (hips, head, left_upper_arm, left_lower_arm, left_hand, right_*, left_upper_leg, left_lower_leg, left_foot, right_*, plus chest, neck, left_shoulder, right_shoulder). Validated at build time with HumanoidRig::map_with_overrides.
  • collider_radius / collider_height: applied to the player's Character Controller.

When an avatar is worn, its skinned parts get a Humanoid IK (source Auto): the wearer's trackers drive it locally, and other players' copies follow their replicated trackers. The descriptor's bone map applies to that IK. Parts that carry blendshapes also get Face Tracking and Lip Sync, so faces and mouths work with no setup.

Loading at runtime

ContentManager (crates/zestengine-engine/src/content.rs) lives in the game runtime and in the editor's Play mode. Gameplay drives it through ctx:

// Load only (validate + upload); result arrives as ContentEvent::Loaded.
let req = ctx.load_content("https://example.com/forest.zestenginepak");

// Spawn a prop in front of the player.
let (req, root) = ctx.spawn_content("/home/me/chair.zestenginepak", pos, rot);

// Make an avatar package the player's body.
ctx.spawn_avatar(self.player, avatar_id_or_path);

// Seamless world switch (objects marked keep_on_scene_change come along).
ctx.enter_world(world_id);

ctx.unload_content(id);

for e in ctx.content_events() {
    match e {
        ContentEvent::Progress { request, stage } => {}
        ContentEvent::Loaded { request, info } => {}      // info.id = content hash
        ContentEvent::Spawned { request, info, root } => {}
        ContentEvent::WorldEntered { request, info } => {}
        ContentEvent::Failed { request, source, error } => {}
        ContentEvent::Unloaded { id } => {}
    }
}

source is a file path, an http(s):// URL, or the content id (hash) of a package loaded before.

Each request runs on a worker thread, mirroring the scene loader:

  1. Resolve the source. Ids come straight from the cache; URLs are looked up in the cache index first, then downloaded through the ContentFetcher.
  2. Open the archive and validate the manifest against the limits of its kind.
  3. Extract into the cache (<cache>/<content hash>/), verifying every file's size and SHA-256 and the content hash. RON assets are rewritten so packaged paths become absolute paths into the extraction directory (packages can't collide with game assets or each other); relative paths that aren't in the package still resolve against the game's own assets, so content can reuse base-game assets. Unknown components are dropped and BC blobs installed. The directory only appears once complete; a cached extraction is reused when the hash and the game's component set match.
  4. Decode models and textures and upload them on the transfer queue (scene_loader::load_on_worker_checked), with the real triangle count and texture memory checked before anything is uploaded.

The main thread then:

  • World: hands the decoded scene to SceneFlow::switch_to_loaded, so the switch is the same seamless switch as ctx.load_scene (old world keeps running until the new one is ready, kept objects carried over).
  • Prop / Avatar: appends the hierarchy to the current scene with fresh object ids (id references inside component data follow), tagged with an origin for unloading. Later spawns of the same package reuse the installed meshes and textures. Avatars are parented to the player, replace its previous avatar, and move its camera / capsule to the descriptor.

Downloads: the engine has no TLS client in its dependency tree, so the built-in HttpFetcher handles plain http:// (redirects, chunked encoding, size cap). For HTTPS, a CDN or authentication, install a fetcher:

        // ureq / reqwest / platform HTTP here
    }
}
content_manager.set_fetcher(Arc::new(MyFetcher));

Cache

The per-user cache defaults to <cache dir>/<game title>/content (GameConfig::content_cache overrides it; the editor uses <project>/.zestengine_content). It holds one directory per content hash, sources.ron (URL -> hash, so a URL isn't downloaded twice) and downloads/. ContentCache::prune(max_bytes, keep) evicts least-recently-used packages; evict(hash) removes one.

Developer overlay

Set GameConfig::content_overlay (or ZESTENGINE_CONTENT_OVERLAY=1) and press F8 in a built game: it lists .zestenginepak files in <cache>/inbox, <assets>/content and ZESTENGINE_CONTENT_DIR, with Spawn / Wear / Enter buttons, the loaded packages with Unload, and a log of content events and warnings.

Safety model (untrusted content)

  • No native code, ever. Nothing in a package is executed. File types are whitelisted at build and load; anything else (including .so/.dll) is dropped. Precompiled shader binaries (.spv) are never packed or extracted; shader sources are compiled by the game and #include is rejected, so a shader can't read local files at compile time.

  • No import hooks. Model import hooks (ModelImportHook, IMP-6) are native plugin code, so they are editor-only. They only run after the editor's plugin loader enabled them, never in the standalone player, never inside content extraction (ContentCache::extract suppresses them), and never for any file under a ContentCache root (import_hooks::mark_untrusted_root), even in the editor. If UGC ever needs import customisation it gets data-only import steps in the .meta, never code.

  • Integrity. Every file's size and SHA-256 is checked against the manifest and the manifest's file table against the content hash; a mismatch aborts the load and leaves nothing in the cache.

  • Paths. Manifest paths must be normalized relative paths (no .., no absolute or drive paths, no duplicates). On extraction, strings in RON assets that point outside the package (absolute, ~/, or climbing with ..) are blanked with a warning. glTF buffer/image URIs must resolve inside the package or the package is refused.

  • Resource limits (ContentLimits::for_kind, overridable with ContentManager::set_limits):

    WorldAvatarProp
    package size512 MiB64 MiB64 MiB
    unpacked size1 GiB200 MiB200 MiB
    files4096512512

    Besides the hard limits, content gets a performance rank (Excellent to Very Poor) from its triangles, materials, bones, blendshapes and texture memory (zestengine_assets::perf_rank, budgets per kind and Desktop / Mobile tier; PackageStats records the counts). Players set a minimum rank, a maximum number of shown avatars and a culling distance; other players' avatars that fail are not drawn (Tools > Performance in the editor).

    Limits are checked on the manifest's claims (fail fast), on archive entry sizes while reading (zip-bomb guard: reads are capped at the declared size), and on the measured data before upload, with errors naming each exceeded limit. BC cache blobs are fully validated (format, dimensions, per-mip byte counts) before they reach the GPU upload.

  • Unknown components are dropped with warnings; component data that fails to deserialize is dropped by the registry as for any scene.

Known gaps: an FBX can name an absolute texture path that the importer tries before the packaged relative one (read-only, local rendering only; prefer glb for UGC). Other scenes a world links to by portal load through the normal scene path, so the per-package limits only apply to the entry scene.

Limitations

  • Unloading a prop/avatar removes its objects immediately; its GPU meshes and textures stay allocated until the next world switch (the renderer frees resources per scene, not per handle). Spawning the same package again reuses them.
  • Worn avatars replicate (content id + URL on the player's Network Avatar, see networking.md); one worn from a local file only reaches peers that already cached it.
  • HTTPS needs a game-provided fetcher (no TLS client in the dependency tree).
  • Custom shaders need glslc on the player's machine.
  • Only one world switch per package can be pending at a time; content loaded in the editor's Play mode is forgotten when Play stops.

WASM component modules

A package may carry .wasm modules that a Wasm Script component loads (the component's module field is path-rewritten like any other asset reference). The module's manifest actions show up in the event-binding dropdowns of other objects, and bindings call them with typed arguments. The ABI (manifest, value encoding, exports, host imports) is documented in crates/zestengine-core/src/wasm/mod.rs; guest/zest-guest is a Rust helper for authors.

Validation, with no guest code run, at build (errors) and again at extraction (the package is refused):

  • file size at most ContentLimits::max_wasm_bytes (1 MiB for worlds, 512 KiB for props), at most max_wasm_modules modules (16 / 4; avatars carry none);
  • imports only from the host namespace and only functions on the allowlist; no WASI, no imported memory, table or global;
  • exactly one exported 32-bit memory within the page cap (64 pages = 4 MiB);
  • a valid zest_manifest custom section (modules in packages must have one), declaring only the capabilities untrusted content may use (state, events, read; never invoke), and the exports its actions and properties need.

At run time a module inside an extracted package is untrusted: tighter limits (1 M instructions per call, 4 MiB, 256 KiB guest stack), and other objects' bindings may call only actions its manifest flags ugc_safe, and only if allow_wasm_actions is set in the package kind's limits. The content manager registers each extracted package's files folder as untrusted (zestengine_core::wasm::register_untrusted_root); the trust of a module is its location. A trap (out of fuel, stack overflow, unreachable) disables the component and logs one error.

Game-wide mods and further scripting work

Game mods reuse these archives and sandboxed components for asset replacements, additive scenes, explicit game-granted action permissions, offline UUID identities and multiplayer profile matching. A game's mod API version is separate from the engine's WASM ABI and package format versions.

Further scripting APIs (for example additional physics queries or a visual scripting graph interpreter) can extend the existing deferred-command model. They should share its permission and resource boundaries rather than introduce a second unrestricted execution path.

Native plugin dylibs (the editor's hot-reload path) are never an option for untrusted content.

Game mods

Mods reuse .zestenginepak, the existing asset loaders and sandboxed WASM components. A mod adds files/mod.ron to the package. It can replace assets exposed by a game and append objects to exposed scenes. The same profile runs in editor Play, built games and dedicated servers.

Identity without a registry

A mod has a canonical UUID v4, generated once by ModManifest::new or the editor's Create mod manifest (new UUID) button. Generation uses the engine's OS-random UUID generator and needs no internet service. Accidental collisions are negligibly unlikely. Keep the UUID when publishing updates; generate a new one for an independent fork. Names and authors are display metadata.

A UUID identifies a mod; it is not an authorship certificate. Multiplayer compares the ordered list of UUIDs, exact versions and package content hashes, plus the target game ID and mod API version. Copying an ID onto different contents does not pass that comparison. The package SHA-256 file table covers mod.ron and every packaged payload, and payload hashes are checked at install and extraction.

Game setup

Open Project Settings > Mods:

  1. Set a stable Game ID and a Mod API version. Keep the game ID stable across display-name changes; increment the API when the game's mod contract breaks.
  2. Expose exact asset paths, or directory prefixes ending in /. For example, scenes/main.scene permits replacement or additions to that scene, and items/ permits replacement assets below that directory.
  3. Expose any component actions mod WASM may invoke, as exact Component.Action names, for example Health.Damage.

A mod cannot grant itself additional paths or WASM action permissions. Its manifest must target this game and this API version. Games can disable mods. Native DLL/shared-library plugins are not loaded from mod packages. Mods may use components already linked into the game, including game-specific ones; missing required component types cause loading to fail instead of silently changing gameplay.

Authoring

In Project Settings > Mods > Build a mod package, enter a project-relative manifest filename (for example my-mod.ron) and entry scene, then create the manifest. This does not overwrite an existing file or regenerate its UUID. Edit that manifest to describe the package:

(
    id: "c54364ed-1920-4a08-a962-169bab11a5ec", // example only: generate your own
    name: "Extra equipment",
    author: "Creator",
    version: "1.0.0",
    game_id: "my-game",
    game_api: 1,
    dependencies: [],
    conflicts: [],
    load_after: [],
    overrides: {"items/equipment.ron": "mod-assets/equipment.ron"},
    additions: {"scenes/main.scene": "scenes/equipment.scene"},
    actions: ["Health.Damage"],
)

Paths on the left are game paths; paths on the right are assets in the creator project. The entry scene and assets referenced by the manifest are packaged with their dependencies. The entry scene is not automatically appended: additions declares the scene attachments. An empty entry scene supports a replacement-only mod. Build writes build/content/<uuid>.zestenginepak.

Dependencies use (id: "<uuid>", version: Some("1.0.0")); None accepts any installed version at resolution time. Multiplayer still requires the exact resolved versions. Dependencies must be installed and explicitly enabled. Cycles, missing dependencies and declared conflicts fail validation. load_after orders an enabled mod after another enabled mod. Otherwise profile order decides precedence; later replacements win and produce a warning.

Additive scene objects receive deterministic namespaced IDs, preserving their internal references without colliding with the base scene. Mod asset references use _mods/<uuid>/files/... on every machine, including replicated prefab paths. WASM file references resolve inside each machine's session snapshot. Mod WASM uses bounded memory and fuel, has no WASI filesystem/network access, runs on the server in multiplayer, and can invoke only the actions granted by the game and requested by the mod. Use the existing Network Object, Network Variables and network spawn facilities to replicate gameplay results.

Installation and profiles

The Mods manager is available in Project Settings and through F10 in a built desktop game. Enter the path to a .zestenginepak, install it, enable the wanted mods, adjust order, then Validate and save profile. Installing an update replaces the installed version with the same UUID. Changes take effect on the next game session or after stopping and restarting editor Play.

The default library is the user's data directory under zestengine/<game-id>/mods; a project without a Game ID uses .zestengine/mods in its project. Packages are stored as <uuid>.zestenginepak. Profiles are profiles/<name>.ron:

(enabled: ["c54364ed-1920-4a08-a962-169bab11a5ec"])

active.profile selects the profile last saved in the manager. The project configuration's mods.profile supplies the fallback name (default). A missing profile means no enabled mods.

For a server, install the packages and profile into its library and set these optional environment variables before startup:

export ZESTENGINE_MOD_DIR=/srv/my-game/mods
export ZESTENGINE_MOD_PROFILE=cooperative

The runtime freezes an asset snapshot before loading scenes or connecting. Changing installed packages does not mutate a running session. Editor Play requires the scene to be saved before applying mods and restores the authored project on Stop. Start modded Play before opening an editor network session; an existing session with a different profile must be disconnected.

Multiplayer and saves

The encrypted handshake includes a digest of the resolved mod lock. The host rejects mismatches before admitting a peer or sending the world. Missing or extra mods, altered contents, differing versions and differing resolved order all fail. This also applies to reconnects and host migration. Protocol version 8 is required on all peers.

A rejection lists the server's required UUIDs, versions and hashes in load order, bounded to fit a handshake packet. Large lists are truncated with an instruction to obtain the full profile from the server operator. Distribute the packages and profile together; no online mod registry or automatic mod download service is required or provided.

Save slots record the same mod lock. Loading an incompatible save logs an error and preserves live state. Old saves with no mod metadata remain compatible with unmodded sessions. Compatibility checks cannot prove a modified client is honest; they prevent accidental content mismatch, not cheating.

Scope and ownership

  • zestengine-core::mods: serializable contracts, UUID validation, permissions, dependency/load-order resolution and save compatibility. No filesystem UI.
  • zestengine-assets::mods: archive building/verification, installation, profiles and asset snapshots. Reuses the existing package format and import validators.
  • zestengine-engine::modding: shared startup lifecycle; modding_ui: shared manager; networking enforces admission and Play enforces save compatibility.
  • zestengine-editor::editor_mods: Play/Stop lifecycle and authoring UI hooks. Dedicated servers use the same engine startup path.

The initial implementation provides manual package distribution and desktop management UI, not a mod catalog, subscriptions, signatures, automatic downloads, a VR-native management panel or hot swapping. Profiles allow one installed version per UUID. Mod snapshots copy project assets, so large projects need additional temporary disk space. Asset dependencies must be packaged; external resources in model formats should be embedded or explicitly replaced alongside the model. Ordinary glTF external buffers/images are rebased on replacement.

VR avatars: height, scaling and full-body calibration

A VR player's avatar should stand at the player's height, put its eyes where the headset is, and have each tracker drive the right body part. ZestEngine measures the player once, keeps the measurements per user, and fits whatever avatar they wear to them. The code is in crates/zestengine-core/src/body.rs (data and math) and crates/zestengine-engine/src/body.rs (devices, the calibration flow, the fit and the body panel).

The player's body

The engine keeps one BodyProfile per user in ZestEngine/body.ron in the user's config folder (%APPDATA%, ~/Library/Application Support, $XDG_CONFIG_HOME or ~/.config; ZESTENGINE_CONFIG_DIR overrides it; on Android the app's internal storage). Every ZestEngine game and the editor share it, so a player measures once. It holds:

  • measured_eye_height: the headset's height above the floor while standing straight, averaged over one second. Samples further than three median absolute deviations (at least 1 cm) from the median are dropped; the measurement is refused if the headset moved more than 6 cm.
  • height_override_cm: the player's own entry (top of the head), which wins over the measurement. Standing height = eye height + 11 cm (EYE_TO_CROWN).
  • arm_span: controller-to-controller distance in the T-pose.
  • floor_offset: a play-area floor correction from the floor check, taken off every tracked height.
  • roles: device id -> tracker role (or ignored). Devices not listed keep the role they report.
  • tpose: the stage-space tracker poses of the last T-pose. Tracker offsets are solved from it for whichever avatar is worn, so switching avatars needs no new T-pose.

Tracker devices

Head and hands always come from the headset and controllers. Body trackers come from two places:

  • The OpenXR runtime's trackers (XR_HTCX_vive_tracker_interaction), one device per role path: xr:waist, xr:left_foot, ... The runtime decides which tracker sits on which path (SteamVR's tracker roles); ZestEngine can move a path to another body role or ignore it.
  • SlimeVR, through the server's driver bridge (slimevr.rs), one device per server tracker keyed by its serial: slimevr:<serial>.

Each frame BodyTracking::assemble puts every device in its role's slot (the player's choice, else the device's own; the first device on a slot wins) and applies the floor offset.

Calibration

The body menu runs three guided steps, each with a prompt and a three second countdown:

  1. Stand straight: one second of headset samples gives the eye height.
  2. T-pose: arms out at shoulder height. Held for 0.6 s, then captured. In a full calibration with "Assign roles from the T-pose" on, every tracker is matched to the body role whose T-pose position it is nearest to (relative to the headset's position and facing, scaled by the eye height and arm span; each role used once, solved exactly over all trackers at once, so left and right never swap; a tracker far from every role stays unassigned). The arm span is taken from the controllers.
  3. Floor check (optional): put a controller on the floor and pull its trigger. The floor moves so that controller sits 3.5 cm up; the measurements taken against the old floor move with it. A trigger pulled higher than 35 cm is ignored (that was a click on the panel). Skip leaves the floor as it is.

Quick recalibrate runs only the T-pose and keeps the roles. Height runs only the first step. ctx.calibrate_trackers() captures the T-pose on the spot.

The offsets come from humanoid::calibrate_tpose: the avatar's rest pose, at the size the player stands in it (see model_to_stage below), is lined up under the headset and turned to face where it faces, and each tracker stores its rigid offset to its bone. That offset carries the difference between where the player's hips and feet are and where the avatar's are, so standing straight puts the avatar's hips and feet at its own rest heights. Before any T-pose, default_calibration maps an ideal headset and controllers onto the bones.

Fitting the avatar

VR Player has avatar_scaling (default Scale avatar) and match_arm_span:

  • Scale avatar: the avatar is scaled uniformly so its eyes sit at the player's eyes. Its arms scale with it.
  • Scale player: the avatar keeps its size and the VR Player rig (the tracking space) is scaled instead, so the player sees from the avatar's eyes, as a giant or a child would. The headset view, hands and locomotion all follow the rig's scale. An avatar parented under the rig is scaled back so it keeps its size.
  • Off: nothing is scaled.

The avatar's eye height comes from its eye bones, else its head bone plus a proportional offset, measured from the floor it stands on (measure_avatar); its arm span is wrist to wrist with the arms straight. fit_avatar returns the avatar factor, the tracking factor and model_to_stage (avatar model units to tracking-space meters, the same in both scaling modes: the avatar is player-sized as the player stands in it).

With Match arm span, hand targets move avatar span / player span as far from the shoulders (BodyIkSettings::arm_reach), so long or short avatar arms reach naturally without non-uniform scaling.

The fit scales the avatar's Avatar Descriptor root (a worn package), else the Humanoid IK object, and writes only scales it has not been told about: if gameplay changes the avatar's scale, that becomes its new authored size. Fits run only in Play (the editor never saves a fitted scale) and only while a headset is running.

Networking

The owner's Network Avatar (Drive From VR or Follow Local Player) sends the fitted avatar scale and the measured eye height as the synced variables zestengine.avatar_scale and zestengine.eye_height (reliable, late joiners catch up). Remote copies expose them as avatar_scale / player_eye_height and the avatar under a remote Network Avatar is scaled by avatar_scale, so everyone sees the same size. The replicated tracker targets are already calibrated bone targets in world space (in Scale player mode they are at the avatar's size), so remote IK needs nothing else. A worn avatar under a remote player's Network Avatar follows that player's replicated targets.

The body menu

In a headset, the VR Player's Body menu action (Menu, the menu button in the VR Controllers scheme) opens a panel in front of the player: Calibrate, Quick recalibrate, Height and Done, the height with +/- 1 cm and "Use measured", the detected trackers with their roles (cycle with < and >; duplicates show red), and a live front view of the posed avatar with the trackers drawn on it. Point at it with either controller and pull the trigger, or poke it with a controller. During calibration it shows the step, the prompt and the countdown. Set the action empty to keep the button for the game.

In the editor, Windows > Body Tracking shows the same panel as a window (roles can be set there without a headset; trackers seen before are listed), and the VR Tools window's Body Calibration opens the in-headset panel in the editor's VR mode.

Gameplay API

let h = ctx.player_height();        // m, to the top of the head
let s = ctx.avatar_scale();         // the local avatar's fit
let body = ctx.body();              // eye height, arm span, measured, calibrated, ...
ctx.request_height_calibration();   // stand straight for a moment

Limits

  • Runtime trackers are identified by their OpenXR role path, not their serial: XR_HTCX_vive_tracker_interaction binds actions per role path, and XR_MNDX_xdev_space is not used yet. Moving a physical tracker to another SteamVR role moves its saved ZestEngine role with it.
  • Fingers are not tracked yet.

Importing Megascans / Fab assets and recognising MetaHuman packages (IMP-8)

ZestEngine does not download anything and there is no public Fab API. You download a pack yourself (from https://www.fab.com, Quixel Bridge, Sketchfab, a marketplace, ...), then import the folder or the .zip. The importer only reads your files and writes native assets into your project. Nothing is bundled and no Quixel or Epic code is used.

Code: zestengine-assets/src/{pack_zip,tex_roles,megascans,pack_scan,pack_convert,mhpkg}.rs, editor zestengine-engine/src/pack_import_ui.rs. Modelled on the Unity package converter (unity_package.rs, unity_convert.rs, docs/shaders-unity-compat.md): detect, parse, convert, report what could not be mapped.

Using it

  • Files panel: Create menu (empty area, or the Create button) > Import Megascans / Fab Asset...; or right-click a folder, .zip or .mhpkg > Import Megascans / Fab Asset...; or drop a folder / .zip / .mhpkg from the file manager onto the panel.
  • The dialog scans (a zip is extracted to a temp folder first, with size limits) and lists the assets it found. Pick a type (3D asset, plant, surface, atlas, decal, imperfection, brush), check the texture roles (every row has a dropdown; a "guessed" badge marks short names like _N), set the real-world size of tiling surfaces, the target folder (default megascans), the texture size cap and what to do if the folder already exists. Import runs as a task with progress.
  • Browse on Fab opens https://www.fab.com in your browser. Watch the Downloads folder (off by default) lists ~/Downloads every 3 seconds and offers to import a new .zip / .mhpkg / folder once it has stopped growing. No network.

What a Megascans export looks like (checked against 82 real Fab downloads)

One folder per asset id (5-12 lowercase letters / digits, e.g. xb5ebhf):

  • Models: <id>.fbx, or <id>_VarA_LOD0.fbx, <id>_VarB_LOD0.fbx, ... (_LODn numbering is read numerically, so LOD10 sorts after LOD2).
  • Textures: <id>_<res>_<Role>.jpg with Albedo or BaseColor/Basecolor, Normal, Roughness, Gloss, AO, Cavity, Bump, Displacement, Specular, Opacity, Translucency, Metalness, Fuzz, and packed ORM / Occlusion-Roughness-Metallic; plants add <id>_8K_Billboard_<Role>.jpg.
  • Fab downloads carry no JSON. Quixel Bridge exports carry <id>.json, read leniently (every field optional, unknown fields ignored, numbers may be strings): semanticTags.asset_type / categories[0] for the type, semanticTags.name, meta[] with scanArea (2x2, 2 x 2 m, 50 cm) for the real-world size, meshes[].uris[].lod, maps[]. The JSON schema is from the documentation; no export JSON was on the development machine, so it is untested against a real one.

Without JSON the type is inferred: a mesh with billboard maps, or with opacity and translucency, is a plant; a mesh is a 3D asset; textures only is a surface. Change it in the dialog if that is wrong.

Safety

Archives are untrusted. pack_zip.rs rejects .., absolute and drive paths and backslash tricks, skips symlinks, encrypted and repeated (also case-only different) names, limits entries (50 000), a single entry (4 GiB), the total (24 GiB) and the compression ratio (1000x for entries over 1 MiB), and counts the bytes actually written rather than trusting the header. Folder scans never follow symlinks and stop at 100 000 files.

Not done

  • Translucency and fuzz maps have no shader term; they are reported (Not supported yet) and dropped.
  • Atlases are not sliced; displacement scale is a fixed default, the JSON min / max intensity is not read.
  • A LOD Group is only wired for single-part models.
  • The watcher's on/off state is not saved between sessions.
  • Visual results (how a converted material and the dialog look) were not checked in a running editor.

Flux: realtime global illumination

Flux is ZestEngine's built-in realtime GI: a Lumen-style screen-space technique that needs no bake and no RT cores. Each frame it places sparse screen-space probes (one per 4x4 pixel block), reconstructs world position + normal from a depth prepass, and cosine-traces them against a cached Global Distance Field — a merged 3D distance + nearest-instance texture built from per-mesh SDFs. Emissive surfaces are sampled analytically as sphere area lights (NEE), so emitter bounce is smooth instead of noisy. Results temporally accumulate with reprojection (and a per-frame jittered seed so the noise actually converges), are bilaterally upsampled to full resolution in the forward shader, and feed back into the next frame's trace for cheap multi-bounce (a radiance cache).

The whole trace is folded into the main command buffer — no extra submits or fence stalls, on the order of 0.06 ms/frame of CPU. The result is soft, atmospheric, and fully dynamic: move a light or an emissive object and the bounce updates live. It's tuned per-scene in the Environment tab (intensity, quality preset, bounces, smoothing, GDF resolution). Baked lightmaps stay available as the zero-runtime-cost path for VR / low-end targets (mixed lighting).

zestengine standard shader

The single default shader used by every world and avatar, on PC and mobile. Inspired by Poiyomi: one heavily configurable uber-shader instead of many small shaders, so creators toggle features instead of writing GLSL.

Flux math

The shared helpers in crates/zestengine-render/shaders/flux_common.glsl provide the sampling and lighting calculations used by Flux:

  • Screen probes use four real spherical-harmonic coefficients, with basis (1/sqrt(4*pi), sqrt(3/(4*pi)) * (-y, z, -x)). The signs and order preserve the existing screen-probe buffer convention. This is distinct from the positive-axis convention in the baked/world-volume probes.
  • Diffuse irradiance is the hemispherical integral of incoming radiance times the cosine with the surface normal. For degree zero and one, the convolution factors are pi and 2*pi/3. The helper evaluates those four RGB coefficients directly. The resolve still uses only the directional ratio; the denoised scalar gather supplies brightness. See Ramamoorthi and Hanrahan (2001), An Efficient Representation for Irradiance Environment Maps, equations 3, 7 and 9. The basis normalization is computed from pi.
  • Hemisphere sampling projects a uniformly sampled disk onto a hemisphere: radius squared is uniform and height is sqrt(1-radius_squared). This is Malley's method, explained in Physically Based Rendering, section A.5.3. A unit-quaternion rotation carries the local direction into the surface frame. The north/south chart boundary remains at normal.z = -0.5 to preserve the directional-bin convention shared by tracing, temporal history and denoising.
  • The RGB firefly limiter applies one scale so that the largest channel does not exceed the configured ceiling, preserving color ratios.

gpu_tests::flux_math exercises the actual production GLSL against analytic constant/linear lighting integrals, the spherical-harmonic addition theorem, cosine-distribution moments, both poles, chart boundaries, sampling endpoints, wall-normal continuity and RGB ratios. Run it with:

cargo test -p zestengine-render --lib gpu_tests::flux_math -- --nocapture --test-threads=1

As with other GPU tests, a machine without a usable Vulkan device reports a skip. A compilation or skipped test is not evidence of numerical correctness.

Why an uber-shader

Poiyomi's model works because creators get a huge feature surface behind checkboxes, and the shader compiler strips everything unused. We replicate that with SPIR-V specialization constants + compile-time variant flags:

  • Authoring time: every feature is a material property in the editor.
  • Build/publish time: the material's enabled-feature set selects (or bakes) a shader variant; disabled features cost zero GPU time.
  • Runtime: variants are cached in a pipeline cache keyed by (feature_bits, vertex_layout, render_state, tier).

HLSL

.hlsl files use the same directives and bindings. Implement float4 zestengine_frag(ZestEngineInput i); the engine adds the main entry point. ZestEngineInput has world_pos, normal, uv, color, tangent, uv1, frag_coord (SV_Position) and front_facing. Every texture is a Texture2D x with a SamplerState sampler_x at the same binding (glslc's -fauto-combined-image-sampler merges them into the combined samplers the pipeline uses); ZESTENGINE_SAMPLE(x, uv) expands to x.Sample(sampler_x, uv). The material block is a cbuffer with explicit packoffsets matching the std140 layout, keywords are [[vk::constant_id(N)]] const values, matrices are column-major as the engine writes them (use mul(M, v)). The helper functions have the same names and signatures as in GLSL. Compiled with glslc -x hlsl -fshader-stage=frag.

// @shader "Rim Glow"
// @property tint "Tint" Color = (1, 1, 1, 1)
// @feature RIM "Rim"
// @property rim_color "Rim Color" Color3(HDR) = (2, 2, 2)
// @end
float4 zestengine_frag(ZestEngineInput i) {
    float4 albedo = ZESTENGINE_SAMPLE(t_albedo, i.uv) * tint;
    float3 n = normalize(i.front_facing ? i.normal : -i.normal);
    float3 c = albedo.rgb * (zestengine_direct_lambert(i.world_pos, n) + zestengine_baked_gi(i.world_pos, n));
    if (RIM) c += rim_color * pow(1.0 - saturate(dot(n, normalize(u_camera_pos - i.world_pos))), 3.0);
    return float4(zestengine_postfx(c, i.frag_coord.xy), albedo.a);
}

Keyword variants (shader_feature model)

One shader file contains every feature; @keyword / @feature properties decide which of them a material's GPU program contains.

  • At runtime the shader compiles once to a SPIR-V module whose keywords are specialization constants. Each material's keyword set is part of its pipeline key, so every distinct set gets its own pipeline, built lazily the first time a material with that set draws and cached afterwards. When the driver builds a specialized pipeline it folds the constants, so if (GLITTER) { ... } with GLITTER off is removed: no branch, no texture sample, no register pressure from the disabled code. Toggling a keyword in the Inspector switches pipelines without recompiling GLSL.
  • Non-keyword properties (sliders, colours) are uniform reads: changing them never creates a variant. Use @keyword for anything that gates sizeable code or texture fetches, plain properties for values.
  • Game builds (bundle.rs) precompile every shader to a .spv sidecar (players need no glslc) and additionally bake the exact keyword sets their scenes and .material files use into <shader>.variants/<hash>.spv, with the keywords compiled as plain constants so glslc's optimizer strips the disabled code from the SPIR-V itself. The runtime prefers a baked variant when one exists and otherwise falls back to specializing the shared module.
  • Cost model: variant count is bounded by the keyword combinations materials actually use (not 2^N); each costs one pipeline object. The test zestengine_toon_variants_strip_disabled_features checks that ZestEngine Toon's Simple variant compiles to roughly half the SPIR-V of Heavy with a quarter of the texture samples, and that the heavy-only samplers (dissolve, glitter, decal, detail, parallax, second matcap, hair shift) are absent.

Vertex hook

A custom GLSL shader can move its own vertices: waving grass, banners, flags, breathing, shatter. Put a function in a // @vertex ... // @endvertex section anywhere in the file:

// @property sway "Sway (m)" Range(0, 1) = 0.15
// @vertex
void zestengine_vertex(inout VertexData v) {
    float h = clamp(v.position.y / 2.0, 0.0, 1.0);
    v.world_offset.x += sin(v.time * 2.0 + v.world_position.x) * sway * h * h;
}
// @endvertex
void main() { /* the fragment stage, unchanged */ }

Line numbers in compile errors are the file's own. HLSL shaders have no hook.

One hook, every pass. The engine splices your function into its own vertex shaders and builds them with glslc the first time a pipeline needs each one: the main pass, the depth prepass, the XR (multiview) pass and planar mirrors share one module (standard.vert), so the depth prepass and the EQUAL-tested main pass compute bit-identical positions; the shadow pass has its own (shadow.vert) that runs the same function, so swaying grass casts the shadow of the swayed surface. Because the shadow depends on time, a layer holding a hooked caster re-renders every frame. A shader without a section compiles exactly as before (no extra module, no extra pipeline state; tested).

Limits and conventions:

  • Previous-frame position. The motion vectors (TAA / upscaling) assume the displacement did not change since the last frame, so only the object's own movement shows as velocity. Fast hooks ghost slightly under temporal upscaling.
  • Bounds. Culling uses the mesh's own bounds (DrawCmd::bound_radius): give a swaying object a bound with margin.
  • Cluster path. Custom-shader materials are never drawn through the cluster (virtual geometry) path (they draw the ordinary mesh, like before), so a hook never meets cluster vertex pulling; hooked casters are left out of the cluster shadow batches too and draw as ordinary meshes.
  • GPU-driven batches. Custom shaders were never in the GPU-culled indirect batches; unchanged.
  • Instance colour / param are not given to the hook (the shadow pass has no such stream).
  • glslc at run time. Like every custom shader the hook is compiled when the shader registers (a hook that does not compile fails the shader, naming the line); the other pass modules compile on first use. A game that ships without glslc should keep to fragment-only shaders for now (the hook's SPIR-V is not baked into a sidecar yet).
  • Template. shaders/zestengine_wind_sway.frag ("ZestEngine Wind Sway"): sway amplitude, speed, plant height, gust and wind direction, rooted at object y = 0, lit and shadowed. Copy it as the starting point for foliage, cloth-like props or banners.

Tessellation and displacement (standard shader and custom shaders)

A material can displace its geometry by a height map with hardware tessellation: the material's Tessellate switch (Material inspector, under the Displacement slot) or MaterialParams::tess (TessParams: enabled, scale, midlevel, edge_px, max_factor, phong; .material files carry it, old files load unchanged). The height map is the Displacement texture slot (binding 16, white = peak).

  • Subdivision follows the screen-space length of each triangle edge: an edge is split until its pieces are about edge_px pixels long, up to max_factor (at most 64). The level of an edge depends only on its two world positions and the camera, so neighbouring triangles agree and the surface has no cracks.
  • Shape. New vertices are placed by Phong tessellation (phong 0..1 pulls them toward the curved surface the vertex normals imply) and pushed along the smoothed normal by (height - midlevel) * scale (world units). The shading normal comes from the height field's slope in the tangent frame, so lighting follows the displaced surface. The height map is sampled at a mip matching the subdivision. While tessellation is on, parallax mapping is off.
  • Every pass. The material's pipelines get a tessellation control and evaluation stage in the main pass, the depth prepass (same modules and an invariant position: the EQUAL-tested main pass agrees pixel for pixel), the XR multiview pass, planar mirrors and reflection captures (all record_scene_draws), and the shadow pass (shadow.vert -DZE_TESS + tess.tesc/tess.tese -DSHADOW, which tessellate from the SAME camera, so the shadow is cast by the surface the camera sees). Casters with a displaced material draw separately from the shared shadow batches and re-render their layer every frame.
  • Cost. One extra pipeline-key bit (PipelineKey::tess); a material without the switch has no tessellation stages and the same pipelines as before. Displaced materials draw on the CPU path (not in the GPU-culled indirect batches).
  • Cluster path. A tessellated material is never drawn through the cluster path: it falls back to the ordinary mesh draw (and is left out of the cluster shadow batches), like custom shaders.
  • Devices. Needs tessellationShader (and multiviewTessellationShader for the XR pass). Without it the material draws flat (use parallax mapping there). A compute pre-subdivision fallback was considered and not built: tessellation hardware is universal on desktop GPUs, absent mainly on some mobile / standalone-VR parts (where subdividing a mesh every frame is the wrong cost anyway), and a fallback would need its own copy of the shadow / prepass / XR plumbing to stay consistent.
  • Mesh needs. Triangle lists with normals, UVs and tangents (the tangent's handedness picks the bitangent); the mesh should be reasonably dense (the patch is the original triangle). Water, outline and fur draws are not tessellated.
  • Bounds. Culling uses the original mesh's bounds: give a displaced object a bound with margin.

Rules this work follows

  • Property names are the identifiers Unity serialises into every .mat file, and the meaning of their values comes from the shaders' public documentation (links below) and the labels the shaders show in the inspector.
  • The converter scans .shader files for the declared shader name (Shader "...") and uses it to identify the material mapping.
  • Licences are recorded below for information; nothing here depends on them.

How conversion works

  1. Read the Unity .mat (text YAML; unity_mat.rs). Tolerates Unity versions, the older first:/second: layout, multi-document files and garbage. Binary .mat files are reported (switch Unity to Force Text).
  2. Identify the shader: built-in Standard by GUID; then by name (from the .shader file the material's shader GUID points at, e.g. .poiyomi/Poiyomi Toon, Hidden/Locked/.poiyomi/..., Mochie/Standard, lilToon, VRM/MToon); then by property signature for locked / renamed shaders.
  3. Map (unity_convert.rs) through alias tables into a ZestEngine material. Colours are converted sRGB to linear (HDR emission colours are stored linear by Unity and are kept), tiling/offset is carried, alpha mode from the shader's mode property (or keywords / render queue), cull mode, cutoff, emission, matcaps, rim, shadow layers, normal map, outline.
  4. Resolve textures: Unity GUIDs are looked up through the .meta files of the folder you point at; the textures are copied to textures/unity/ and given the right import kind with ensure_first_import_for_slot (sRGB colour, normal map). Metallic / smoothness / occlusion are repacked into one ORM texture (R occlusion, G roughness = 1 - smoothness, B metallic). Formats the engine does not load (PSD, TIFF, DDS) are reported.
  5. Write materials/unity/<name>.material and <name>.convert.txt beside it. The report lists Mapped, Approximated, Not supported yet, unmapped properties with a value, and a one-line list of zero / empty ones. Nothing is dropped silently.

Entry points (Files panel context menu): Convert Unity Material... on a .mat, Convert Unity folder... on a directory (task with progress and a summary notification), Import Unity package... on a .unitypackage (gzip tar, read with flate2 already in the tree; extracted to a temp folder, then converted as a folder). The model importer's Search and Remap picks converted materials by name (the .material is named after the Unity material, which is the FBX material name); unity_convert::add_to_model_remap fills the remap table directly.

Dedicated server

zestengine-server (NET-2) hosts a project scene with no window, GPU, audio device or headset. It is the same gameplay, physics and networking code the player runs (zestengine_engine::server::HeadlessHost plus a hosting NetSession), driven by a fixed tick loop. The Network Manager's dedicated mode is forced on: the server gets no player of its own; every joiner gets the Network Manager's player prefab at a Spawn Point (same rules as a player-host).

Build

cargo build --release -p zestengine-server        # target/release/zestengine-server
just server <project-dir>                          # debug build + run

The crate depends on zestengine-engine with default-features = false, so the client feature is off. cargo tree -p zestengine-server -e normal has none of ash, winit, egui, cpal, rodio, gilrs, openxr, audionimbus, gpu-allocator, shaderc, zestengine-render or zestengine-xr; the renderer is the inert stand-in zestengine-render-lite. Direct dependencies: zestengine-engine, zestengine-core, anyhow, serde, ron, tracing, tracing-subscriber, libc (and windows-sys on Windows).

Behaviour

  • Tick loop: a monotonic accumulator yields whole fixed ticks; at most max_catch_up_ticks run per wake-up, the rest of the backlog is dropped (a rate-limited server overloaded warning) so a stall cannot snowball. Between ticks it sleeps (in slices of at most 50 ms so a stop is prompt) and spins only the last 1.5 ms. Inbound packets are read once per tick, so latency adds up to one tick.
  • Stats: every stats_interval seconds one line: ticks (and per second), mean and max tick ms, players, bytes in/out and rates.
  • Joining: the engine's handshake rejects a wrong protocol version, wrong password and a full session with an explanatory reason. Joins and leaves are logged with the player id and the short fingerprint.
  • Console (stdin): status, players, stats, kick <id> [reason], ban <id|fingerprint> [30m|2h|7d|perm] [reason], unban <fingerprint>, bans, say <text>, scene <path>, save, reload, restart [addr], shutdown [addr], quit, help (plus interest when interest management is on). Without a stdin (a service manager) the console ends quietly. The same commands arrive over UDP as signed remote admin (below).
  • Shutdown: SIGTERM, SIGINT (Ctrl+C), Ctrl+Break and console close on Windows, or quit. The server stops ticking, sends every player a close notice with the reason ("server shutting down"), closes the socket, flushes the log and exits 0. A second signal exits at once (130).
  • Identity: the server keeps its own Ed25519 identity on disk; it is not shared with a player install. Clients pin it on first join (trust on first use).
  • Authority and validation (NET-4): the server is the authority for everything and checks what clients send: rate limits, NaN and bounds, movement budgets with teleport correction, VR pose limits, ownership rules (flagged objects, in reach, free, cooldown), RPC permissions, a spawn allow-list (none by default), size limits, timestamps, forged ids. Violations are counted per peer, logged rate limited, scored, and lead to a warning, muting, a kick with a reason and a ban by player id (bans.ron). The stats line shows the violation and muted counts. No player address is sent to other players. Details and the rule table: docs/networking.md.

Content roles (NetRole)

Every scene object and every component has a role: Both (the default; old scenes mean this), Client (only players have it) or Server (only the dedicated server has it). A dedicated server removes Client content when it loads a scene and from every prefab or network spawn; a player that only ever joins servers removes Server content (zestengine_core::set_process_role(NetRole::Client), the player keeps Both by default so offline play and listen hosts are unchanged); the editor keeps everything.

Rules

  • An object's role hides it from the other side with its whole subtree. A child cannot be more permissive than a missing parent: a Both child of a Client object is gone on a server too.
  • A component's effective role is the object's per-component override if it has one, else the type's default. Overrides are keyed like prefab component keys (Kind, Kind#1 for a second one), stored in the scene entry (net_role, component_roles; both omitted when default) and are ordinary prefab-overridable properties (revert, apply, variants).
  • A kept component may still hold an object id of a stripped object (a trigger pointing at a client-only effect, an event binding). It resolves to "missing" (no crash) and the load logs one warning naming both objects (Root/Zone [Trigger Events] references stripped object Root/Smoke).
  • A game component declares its default with const NET_ROLE: NetRole = NetRole::Server; on its TypedComponent impl. Pattern for server-only logic: also put it behind your crate's own cargo feature so the code is not compiled into the client binary.

Server services (NET-6)

Persistent state

Add a Persistent State component (Add Component > Network) to a scene object and the server keeps it across restarts. Flags: transform (position, rotation, scale), variables (the object's Network Variables), per_player (on the player prefab's root: its Network Variables are saved under the owner's player id and handed back when that player joins again, the prefab-spawned object being a different one every session).

<state_dir>/world.state     per scene: flagged objects by scene object id (transform, variables)
<state_dir>/players.state   per player id (fingerprint): name, first/last seen, sessions, saved variables
<state_dir>/bans.ron        bans (engine format)
<state_dir>/identity.key    the server's signing key
  • Restored when the scene loads (at start and after every scene switch); variables are written through the session (NetSession::set_var), so players that join later see them. Player data is restored as soon as the joiner's player object exists, and kept current every tick; nothing is restored for a player id the server has not seen.
  • Written every persist_interval seconds, on the save command and at shutdown. Unchanged state is not rewritten, and a server whose project flags nothing writes no world.state at all. Scene objects are copied into the state every 2 s and when scene is used, so a scene switch loses at most that.
  • File format (ZESTSTATE 1 <schema> <bytes> <crc32> line, then RON): a save writes <name>.tmp, syncs it, rotates <name> to .bak1 (.bak1 to .bak2 ... up to persist_keep), renames the temp file into place and syncs the folder. A crash leaves the old or the new generation, never half. A load takes the newest generation whose length and checksum match; a damaged one is moved aside as <name>.corrupt-<unix> (never rotated over a good backup) and logged as an error; with nothing usable the server starts from the authored scene. A file with a newer schema than the server understands is left untouched and never overwritten (the server runs without it and says so).
  • Not persisted: objects spawned at runtime (no stable id), physics velocities (bodies restart at rest), anything not flagged. A scene object's name and id must not change between runs for its state to find it.

For a built server the project folder is the cooked assets/, so the default state folder is build-server/assets/.server/, which a rebuild replaces. In production set state_dir outside the build folder (/var/lib/mygame); it is the one directory that must survive redeploys (identity key, bans, world and player state).

Signed remote admin

admin_port opens a UDP port that takes the console's commands from holders of an admin key. Make one on your machine, list the public half in server.ron, and the server logs its own key at start (server key ...):

zestengine-admin keygen --out ops.key
# server.ron:  admin_port: 9100,  admin_keys: [(name: "ops", key: "<printed hex>", role: Admin)],
zestengine-admin --server host:9100 --server-key <server key> --key ops.key players
zestengine-admin --server host:9100 --server-key <server key> --key ops.key ban 7 2h griefing

Roles: Observer (status, players, stats, bans, interest, help), Moderator (+ kick, ban, unban, say), Admin (+ scene, save, reload, restart, shutdown). The console on the host is always Admin. Exit code of the tool: 0 ran, 1 refused or failed, 3 no signed answer.

ProtectionHow
AuthenticationEd25519 signature over a domain tag, the server's public key, and the request; only listed keys act
Replaytimestamp within +/-30 s and not before the server started, and a (key, nonce) seen once; replays get Stale
Cross-server replaythe signature binds the target server's key
Tamperingany changed byte fails the signature; no reply is sent to anything unauthenticated
Amplificationunauthenticated sources get nothing; answers go to the sender of a valid signed request only
Floodingtoken bucket per source IP (10 burst, 5/s) before any signature is checked
Spoofed answersreplies are signed with the server identity and bound to the requesting key and nonce

Replies are signed, not encrypted: do not print secrets in command output. Keep admin_port firewalled to your operators if you can (see "Why admin replies are signed, not encrypted" below). reload re-reads the command line's --config and applies motd, stats_interval, restart_on_scene_end, admin_keys, persist_interval / persist_keep, directory_interval, region, game, game_version, shutdown_redirect; it lists the changed settings that need a restart (port, tick rate, player limit, password, project, ...) and refuses a file that does not validate. restart exits with code 75; shutdown and quit exit 0.

Key rotation without a restart. keys lists the keys in force; key add <name> <64-hex> <observer|moderator|admin> lets a new key sign at once and key remove <name|8+ digits> retires one (Admin only). The changes are an overlay in <state_dir>/admin_keys.ron over server.ron's admin_keys: they survive a restart and a reload, and the effective list is (file keys - removed) + added. The last Admin key cannot be removed, a key cannot be listed twice, and a retired key gets no answer at all, like any unknown key. Rotation: add the new Admin key, check it works, remove the old one.

Reports. A player (or a game script) calls NetSession::report_player(peer, reason), or the RPC zestengine.report with [Int(peer), Str(reason)] aimed at the server. The server checks the target is a connected player other than the reporter and the reason fits a chat line, rate-limits it (3 burst, then one per 5 s), and logs it at warn, keeps the last 200 in memory (reports for Moderators, reports clear empties it) and appends a line to <state_dir>/reports.log with the reporter's and the target's fingerprints. Nobody else receives the report; act on it with ban <fingerprint>.

Bans. ban takes a connected player's id or a 32-digit fingerprint (offline players), an optional duration (30m, 2h, 7d, perm) and a reason (shown to the player, kept in bans.ron); it kicks the player if connected. unban accepts a fingerprint or a unique prefix of 8 or more digits; bans lists them with the time left. They go through the same list the strike system writes (val.bans), so a ban made by either survives restarts.

Account linking (anti-cheat). When a provider can name a client's account (AntiCheatProvider::server_provider_id: an EOS product user id, a Steam id ...), the server links it to the player id once the client is Trusted. A ban of the player (admin ban, or the strike system) also bans the account (a hashed key in the same ban list, so it survives restarts); the same account arriving later under a new player key is removed as soon as the provider names it, and the new key is banned too. The built-in providers name no accounts yet (the test provider can), so this is the plumbing, not a verified EOS/Steam integration. The link itself is kept in memory for the session; the ban is what persists.

Held clients. With anti-cheat require on, a client that is not Trusted yet is in the session but out of the world: it gets no catch-up (scene, objects, variables), no player object, and none of the broadcasts, snapshots, chat or RPCs, until the provider trusts it (then the catch-up and the player object follow) or the pending timeout removes it.

Why admin replies are signed, not encrypted

A reply is a status line, a player list, a ban list or a settings summary: operational data about the server, not secrets (no password, key or token is ever printed, and no command reads one back). Signing (bound to the server identity, the requesting key and the nonce) stops a forged or replayed answer; encryption would only hide player names and fingerprints from someone who can already watch the operator's traffic, and it would need a key agreement and an AEAD on a path that is deliberately a single stateless datagram each way. Where that is not acceptable, bind admin_bind to a VPN or loopback address (or tunnel it); the port is never needed by players. If a future command has to return a secret it must not use this channel.

Server directory

A relay started with --directory is also a server list (zestengine-relay --directory [--dir-ttl 90] [--dir-max 4096] [--dir-per-ip 4] [--dir-allow KEYHEX]). With directory: "relay.example.com" the server sends a signed announcement (name, game, version, scene, region, players / max, port, relay room code, password flag) every directory_interval seconds and a signed delisting at shutdown; a crashed server drops off when the TTL (default 90 s) runs out. Players list with filters (region, game, version, name, hide full / empty / password-protected) using zestengine_relay::directory::query_blocking (cookie handshake and paging are handled).

  • The server cannot be spoofed: the entry is keyed by its Ed25519 identity, announcements are signed, timestamps must grow (a captured packet cannot relist a server that left), the listed address is where the announcement came from.
  • Limits: token buckets per IP for announcements (6 burst, 0.5/s) and queries (8 burst, 2/s) before any signature work, 4 listings per IP, 4096 in all, replies to unauthenticated senders are never larger than the request (queries need a cookie bound to the sender's address, the list itself is paged in packets of at most 1200 bytes).
  • Also new on the relay: --host-rate / --client-rate (bytes per second, defaults 4 000 000 and 1 000 000) replace the fixed room cap.
  • A server behind a NAT sets relay (and optionally relay_room): it opens a room, the directory entry carries the code, players join with it (NetSession::join_with("CODE", ..) with the relay set).

Graceful shutdown

SIGTERM, quit, shutdown and restart save the state, delist, and tell every player why. shutdown 10.0.0.2:9000 (or shutdown_redirect in the config, or a room code) adds [redirect: ...] to the notice; a player's game that was joined to a dedicated server follows it by joining the offered address with the same settings (zestengine_engine::server::follow_redirect; it never follows a listen host's notice).

Deploying a dedicated server (NET-7)

Step by step, from a project to a server players can join and an operator can watch. Reference for the settings and admin commands is docs/dedicated-server.md; the networking model is docs/networking.md.

Status of this guide. The files it uses are generated and unit-tested as text (the generated config parses and validates, the unit contains the hardening lines, the heartbeat / probe / metrics run in a real loopback server). Nothing here was run under systemd or Docker by the people who wrote it: treat the first deployment as a test, with systemd-analyze verify and docker compose config as the first checks.

2. Build

just build-server ~/games/arena          # -> ~/games/arena/build-server/

build-server/ now holds the binary, assets/, server.ron (a development config), run.sh, build-report.txt and deploy/:

deploy/arena.service            hardened systemd unit
deploy/arena@.service           template unit for several instances
deploy/server.ron               production settings (state_dir /var/lib/arena)

deploy/nftables.nft, ufw.sh, logrotate.conf, install.sh, README.txt

The names come from the project name (Arena X becomes arena-x). The game port in the templates is the one the boot scene's Network Manager names (port; 9000 when the scene has no Network Manager), and the admin port is that plus one; the examples below show 9000/9001. Change port in deploy/server.ron (and the firewall files) only if you want something else. The build wipes build-server/ on every run, which is why the production state_dir points at /var/lib/<game> and never at build-server/assets/.server (the development default, <project>/.server, would be inside the folder a rebuild deletes).

Check what the server will actually use before starting it:

./zestengine-server --print-config --config deploy/server.ron

prints the effective settings (file, environment and flags merged; the password and relay token show as "<set>"), validated, and exits.

3. Install on a systemd host

Copy the whole build-server/ folder to the host, then:

sudo deploy/install.sh

The script creates a system user arena, installs the binary and assets to /opt/arena/ (the old assets move to assets.old), puts server.ron and arena.env in /etc/arena/ only if they do not exist (an edited config is never overwritten), and installs the two unit files. It does not enable or start anything and does not touch the firewall. Then:

  1. Edit /etc/arena/server.ron: server_name, max_players, admin keys (section 6).
  2. Edit /etc/arena/arena.env (mode 0600): ZESTENGINE_SERVER_PASSWORD, ZESTENGINE_RELAY_TOKEN.
  3. sudo systemd-analyze verify /etc/systemd/system/arena.service
  4. sudo systemctl enable --now arena
  5. journalctl -u arena -f and /var/log/arena/server.log.

What the unit does (deploy/arena.service):

  • Runs as User=arena (comment in the file shows DynamicUser=yes as the alternative), --no-console (no stdin under a service manager), WorkingDirectory=/opt/arena.
  • StateDirectory=arena creates /var/lib/arena (mode 0700) and makes it the only writable place besides LogsDirectory=arena (/var/log/arena). ProtectSystem=strict, ProtectHome, PrivateTmp, PrivateDevices, NoNewPrivileges, empty capability set, RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX, SystemCallFilter=@system-service, UMask=0077. MemoryDenyWriteExecute is left off because a WASM sandbox with a JIT needs writable and executable pages.
  • Restart=on-failure, RestartForceExitStatus=75, SuccessExitStatus=0: a crash restarts it, the restart admin command (exit code 75) restarts it, a clean shutdown / SIGTERM does not. Five failed starts in a minute stop the loop (StartLimit*).
  • KillSignal=SIGTERM, TimeoutStopSec=10: SIGTERM is graceful (players are told, state is saved); after 10 s systemd sends SIGKILL. A save finishes in far less than that for normal worlds.
  • LimitNOFILE=65536. Optional, commented: CPUAffinity=2 3, Nice=-5, MemoryMax=2G.

state_dir in server.ron and StateDirectory= in the unit must name the same folder (/var/lib/arena). If you change one, change the other.

4. Docker

cd build-server
cp deploy/arena.env.example deploy/arena.env      # then edit
docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml ps    # "healthy" once the heartbeat is fresh

The image is built from the prebuilt binary (no Rust toolchain in the image): debian:stable-slim (the BASE build argument), a non-root user (uid 10001), VOLUME /var/lib/arena, EXPOSE 9000/udp 9001/udp, HEALTHCHECK = zestengine-server --healthcheck, STOPSIGNAL SIGTERM. The compose file adds a named volume for the state folder, restart: unless-stopped (which also honours the exit code 75 of restart), stop_grace_period: 10s, a read-only root file system, cap_drop: [ALL], no-new-privileges, and publishes the game port; the admin port line is commented and bound to 127.0.0.1: expose it only to operators.

The binary is dynamically linked against glibc, so the base image needs a glibc at least as new as your build machine's. For a fully static image use the musl target (section 12) with BASE=gcr.io/distroless/static-debian12:nonroot (remove the useradd line, use uid 65532).

docker compose publishes UDP through the host's NAT; for more than a few hundred packets per second per player consider network_mode: host on a dedicated host instead.

Kubernetes

deploy/kubernetes.yaml is a PersistentVolumeClaim (1 Gi, ReadWriteOnce) for the state folder, a Deployment and a Service. Build and push the image first (section 4's Dockerfile), set image: to your registry path, create the secret with the password and relay token (kubectl create secret generic <game>-env --from-literal=ZESTENGINE_SERVER_PASSWORD=..., the secret is optional in the manifest), then kubectl apply -f deploy/kubernetes.yaml. What the manifest decides: one replica with strategy: Recreate (the saved world, bans and the pinned server identity live in one volume, so two servers must never share it, and an update stops the old pod first); terminationGracePeriodSeconds: 15 so SIGTERM can save and send the shutdown redirect; a non-root user (10001) with a read-only root file system and no capabilities (/tmp and the log folder are emptyDirs); startup and liveness probes that run zestengine-server --healthcheck (the heartbeat file, no network); the Service is type: LoadBalancer for UDP with externalTrafficPolicy: Local so players' real addresses reach the server (bans and rate limits are per address). Your provider's load balancer must support UDP; otherwise switch the Service to NodePort and open that port. The signed admin port is deliberately not in the Service: reach it with kubectl port-forward (UDP needs a tunnel) or a separate internal Service. Not run on a cluster; it is generated text with unit tests.

5. Firewall

deploy/nftables.nft and deploy/ufw.sh are examples, not scripts to run blindly: they open the game port, restrict the admin port to an operators' address range, and keep LAN discovery (47777) closed. Check with nft -c -f deploy/nftables.nft before loading anything. The admin port is also protected by Ed25519 signatures, timestamps and a per-address rate limit, but replies are signed, not encrypted: put it behind a VPN or an allow-list, do not leave it open to the internet.

6. Admin keys

On your own machine:

zestengine-admin keygen --out ~/.config/arena-admin.key     # prints the public key

Paste the public key into admin_keys (uncomment the block and admin_port in server.ron; the shipped placeholder PUT_THE_64_HEX_DIGIT_PUBLIC_KEY_HERE is refused at start, on purpose), roles Observer, Moderator, Admin. The secret key never goes on the server. Operate:

zestengine-admin --server host:9001 --server-key <server public key> --key ~/.config/arena-admin.key status

The server's public key is in its log at start (server key ...) and is the pinned identity (section 7).

Rotating a key, with no downtime: add the new key beside the old one, reload (an Admin key can send it), check the new key works (status), remove the old one, reload again. A key that is removed stops working at the reload. Rotating all keys because of a leak: do the same with the leaked key removed first.

7. State directory: backup, restore, upgrade

state_dir holds everything that cannot be rebuilt:

FileWhat
identity.keyThe server's signing identity. Players pin it on first join and refuse a changed one. Losing it makes returning players' games refuse the server (changed identity), and invalidates every --server-key your operators hold.
bans.ronBans by player id.
world.state*, players.state*Persistent scene objects and per-player data, with persist_keep (default 3) older generations next to each.

Backup: copy the folder while the server runs (files are replaced atomically and each generation is checksummed) or, safer, after systemctl stop:

sudo tar -C /var/lib -czf arena-state-$(date +%F).tgz arena

(For Docker: docker run --rm -v arena_state:/s -v $PWD:/b debian:stable-slim tar -C /s -czf /b/state.tgz ..) Keep identity.key somewhere extra safe (it is 32 secret bytes) and out of shared backups.

Restore: stop the server, replace the folder content with the backup keeping owner arena and mode 0700, start. A damaged current file falls back to the previous generation and the bad one is kept as .corrupt-<unix>.

Move to another machine: copy state_dir (above all identity.key), keep the same address or announce the new one; players are not asked anything because the identity is the same.

Upgrade (new build, same identity): the state folder is outside the build folder, so just replace the binary and assets.

sudo systemctl stop arena                  # or the graceful redirect below
sudo deploy/install.sh                     # copies the binary and assets, keeps /etc/arena and /var/lib/arena
sudo systemctl start arena

A state file written by a newer version is not silently overwritten by an older server (it is reported), so keep the backup from before a version jump and do not run an older build on a newer state folder.

Graceful upgrade with a redirect. Bring up the new version on a second port (or another host), then:

zestengine-admin ... shutdown 203.0.113.9:9010     # players get a notice and their game follows the address

shutdown <addr> and restart <addr> offer the address (host:port or a relay room code) to every player as they are disconnected; shutdown_redirect in server.ron sets a default. The follow itself is implemented in the player and loopback-tested only; verify it with a real client before relying on it.

8. Monitoring

Heartbeat and probe. Every health_interval seconds (5 by default, 0 = off) the server rewrites <state_dir>/health.status (plain key=value: state, updated_unix, pid, ticks, players, tick_mean_ms, bytes_out_per_s, bans ...) and <state_dir>/metrics.prom (Prometheus text format). On a clean stop state=stopped is written.

zestengine-server --healthcheck --config /etc/arena/server.ron      # exit 0 alive, 1 not, 2 bad arguments

needs no network and no keys; it reads only state_dir from the config (so it runs in a container without the project), and fails when the file is missing, stale (default: older than three intervals, at least 30 s) or says anything but running. A hung tick loop stops the heartbeat, so a frozen server is caught too. Use it as a Docker HEALTHCHECK (already in the Dockerfile), a cron job, or a systemd watchdog sidecar. Run as a user that can read state_dir (sudo -u arena).

Metrics.

For Prometheus either read metrics.prom with the node exporter's textfile collector (--collector.textfile.directory=/var/lib/arena, only *.prom files are read), or enable the optional listener:

serving GET /health (200 or 503) and GET /metrics. It is off by default, has no authentication (hence loopback), answers one request at a time with a 1 s timeout, and its numbers are those of the last heartbeat. Put a reverse proxy or an agent in front of it if a remote scraper needs it. Several instances: 9100 + N.

The signed status and stats commands over the admin port are the authoritative view (they run on the server thread); the stats line in the log repeats every stats_interval seconds.

Logs. log_path (the template uses /var/log/arena/server.log) is size-rotated by the server (log_max_mb x log_keep); the same lines go to the journal / docker logs. deploy/logrotate.conf adds daily rotation with compression (copytruncate; raise log_max_mb so the two do not both rotate).

9. Several instances on one host

deploy/arena@.service is a template unit: %i is the instance name and selects /etc/arena/%i.ron, with StateDirectory=arena/%i (so state_dir: "/var/lib/arena/%i" written out in that file).

sudo cp /opt/arena/deploy/instance.ron.example /etc/arena/eu1.ron      # edit port, admin_port, state_dir, server_name
sudo systemctl enable --now arena@eu1

Port allocation rule. Instance number N (0, 1, 2, ...) takes game UDP 9000 + 10*N, admin UDP game + 1, metrics (loopback TCP) 9100 + N. The state folder is /var/lib/arena/<instance>, the log is /var/log/arena/<instance>.log. The gaps leave room to grow without renumbering. Only one instance may answer LAN discovery (47777): write lan_discovery: false in all of them on a public host. Give each instance its own cores with systemctl edit arena@eu1 (CPUAffinity=), and size them as in section 10. Instances share the binary and assets/, so an upgrade restarts them one by one: systemctl restart arena@eu1, wait for --healthcheck, next.

10. Sizing a VPS

Numbers come from the NET-5 scale test (docs/networking.md, "Interest management"): 200 simulated clients walking at 4 m/s and reporting at 15 Hz plus 100 server-simulated NPCs, tick 30 Hz, server part of a tick only, in-memory transport (no kernel packet I/O), optimised dev profile, one machine. Real numbers will be higher; measure your own game with --print-config's settings and the tick_ms_mean series.

Rules of thumb that follow:

  • CPU: the simulation is one thread. One fast core runs one instance of up to about 100 to 200 players with interest management on (the tick budget at 30 Hz is 33 ms). More players means more instances, not more cores per instance. Reserve one extra core per host for the kernel's UDP handling.
  • Interest management is not optional above a few dozen players in a big world: switch it on in server.ron (interest: (enabled: true, radius: 100.0, budget: 12000)).
  • Bandwidth: size by the "Total out" column, with 50 percent headroom, and by your provider's monthly transfer: 2.4 MB/s is about 6 TB per month at full load. A 50-player VR session targets about 3.6 MB/s (see the NET-5 leftovers: not measured against real avatar traffic).
  • Memory: not measured. A scene plus replication state for a few hundred objects is small; plan 512 MB to 1 GB per instance until you measure ps -o rss on your game (this is a guess, not a result).
  • Disk: the cooked assets (build-report.txt) plus a few MB of state.

A practical starting point: a 2 vCPU / 2 GB VPS with 100 to 250 Mbit/s runs one instance for 50 to 100 players comfortably; check tick_ms_mean with real players before adding more.

11. Client connect checklist (PC and Quest)

Before announcing the server:

  1. Server log says hosting "..." on UDP 9000, --healthcheck is 0, the firewall allows UDP 9000 from the internet (test from outside: nc -u -z host 9000 only proves the port is not rejected).
  2. Client and server are built from the same engine version and the same project content (the game's scenes and components must match what the server cooked).
  3. PC: connect with host:9000 (direct) or pick the server from the directory, if directory: is set. If the server has a password, the player enters it (it keys the session encryption).
  4. A second join on another day is not refused for a changed identity (if it is, identity.key changed: section 7).
  5. Quest: same address or the directory; the headset must be on a network that allows outbound UDP to the port (guest and hotel Wi-Fi often do not); mobile hotspots work. Check the headset's clock is right.
  6. A player joins, moves, and appears for a second client; players / status over the admin port shows both; the player count in zestengine_players follows.
  7. restart/shutdown with an address: the players get the notice and (once verified with real clients) follow it.
  8. Behind NAT without a port forward: set relay to a zestengine-relay and give players the room code instead of an address.

Rust API Reference

The API reference is generated by cargo doc from the doc comments in the source, so it always matches the engine you are building against.

CrateWhat it holdsReference

Good places to start in the reference:

  • ecs: the ECS model, systems, stages, run_ordered, entity templates.
  • EcsMoveHost: everything a system can do to the world: move, read and edit other objects, spawn, raycast, play sounds, save, network.
  • TypedComponent: the trait every component implements.
