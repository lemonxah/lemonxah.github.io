ZestEngine

Unity shader compatibility (Poiyomi, Mochie, lilToon, MToon, Standard)

Avatars and props authored in Unity use third-party shaders. Convert Unity Material maps their material values onto ZestEngine shaders (ZestEngine Toon and the PBR standard shader) and writes a report of everything it could not carry over. Gaps become plan tasks (IMPLEMENTATION_PLAN.md, "Shader gaps").

Rules this work follows

  • Property names are the identifiers Unity serialises into every .mat file, and the meaning of their values comes from the shaders' public documentation (links below) and the labels the shaders show in the inspector.
  • The converter scans .shader files for the declared shader name (Shader "...") and uses it to identify the material mapping.
  • Licences are recorded below for information; nothing here depends on them.

UNITY-2 Stencil effectsDone (GUI unverified)The scene depth is now a depth-stencil image (D32_SFLOAT_S8_UINT, else D24_UNORM_S8_UINT / D16_UNORM_S8_UINT; ZESTENGINE_STENCIL=0 keeps plain D32_SFLOAT, where material stencil is ignored). Every colour pass attaches the stencil aspect (cleared to 0): main, depth prepass, Flux prepass, Hi-Z late split, planar mirrors, reflection capture, camera targets and preview, XR (single and multiview, MSAA resolve), impostor / text / VR overlay pipelines. Shadow maps stay depth-only D32; the opaque depth copy is a depth-only copy. MaterialFeatures.stencil (StencilState: reference, read / write mask, per face compare + pass / fail / zfail op, color_mask, depth_write) and the inspector's Stencil section drive a per-pipeline-variant stencil state (all eight Unity compare funcs and ops, front and back faces separate). The default state is inactive and draws byte-identically. The converter maps _StencilRef / _StencilReference / _Stencil, _StencilComp / _StencilCompareFunction, _StencilPass / _StencilPassOp / _StencilOp, _StencilFail*, _StencilZFail*, _StencilReadMask, _StencilWriteMask, the ...Front / ...Back variants, _ColorMask and _ZWrite (only next to stencil / colour masking), and the Poiyomi _StencilType preset (1 = writer: Always + Replace; 2 = reader: Equal; explicit compare / pass values win; the preset numbering is an unverified assumption). Draw order: a writer must draw before its readers: give it a lower render queue (Unity Geometry-1 or Geometry+1). Within one queue the order is the renderer's state sort and gives no guarantee. Materials with a non-default stencil state skip the GPU-driven batches (they draw in strict queue order on the CPU path), and a writer with ZWrite off skips the depth prepass. Not done: a stencil Ref driven per instance or animated; Poiyomi's _StencilType UI presets beyond writer / reader; stencil in custom HLSL Stencil{} blocks of imported .shader files (only material properties are read). Sprite masks use stencil bit 7 (0x80) only, so 3D stencil bits 0..6 and sprite masks do not interact; keep 3D references below 0x80 in scenes with sprite masks.
UNITY-3 Grab passDone (mip chain only for transmission)MaterialFeatures.grab / model grab ("Scene Colour Read" in the inspector): the main pass copies opaque colour + depth before the first transparent or grab draw (the copy the water already used). Custom shaders get u_opaque_color, u_opaque_depth, zestengine_grab(frag, offset_px, fallback), zestengine_grab_blur(frag, offset_px, radius_px, fallback) and zestengine_grab_world_pos. A custom shader with a GRAB toggle that is on sets the feature automatically. The copy has a mip chain only on frames that draw a transmission material (rough transmission, UNITY-8); the grab helpers read mip 0 and blur with a 16-tap jittered disc (coarse above about 20 px). Toon GRAB feature: tint, normal-driven distortion, blur, chromatic split. lilToon refraction mode and Poiyomi grab pass map to it. HLSL custom shaders do not get the grab helpers. The copy is taken only in the main camera pass: reflection captures, planar mirrors and the model preview see the fallback colour.
UNITY-4 Screen FX volumeDoneshaders/zestengine_screenfx.frag ("ZestEngine Screen FX"): a box or sphere mesh re-samples the opaque scene for the pixels where the scene point behind it lies inside the shape (reconstructed from the opaque depth copy), with filtering (hue, saturation, contrast, brightness, tint, invert), shake, distortion, blur, pixelate, chromatic split and noise, soft edge falloff. Mochie Screen FX materials are reported as having no converter (property names are unverified; set the volume up by hand with the presets). Not done: a global (non-mesh) screen volume that follows the camera, and the volume does not apply to transparent objects (it reads the opaque copy).

UNITY-11 Vertex hooksDone (GUI unverified)A custom GLSL shader's // @vertex ... // @endvertex section defines zestengine_vertex(inout VertexData v) (object position / normal / tangent / UVs / colour, model, world_position, world-space world_offset, time, the shader's // @property block, textures, keywords, frame). How conversion works

  1. Read the Unity .mat (text YAML; unity_mat.rs). Tolerates Unity versions, the older first:/second: layout, multi-document files and garbage. Binary .mat files are reported (switch Unity to Force Text).
  2. Identify the shader: built-in Standard by GUID; then by name (from the .shader file the material's shader GUID points at, e.g. .poiyomi/Poiyomi Toon, Hidden/Locked/.poiyomi/..., Mochie/Standard, lilToon, VRM/MToon); then by property signature for locked / renamed shaders.
  3. Map (unity_convert.rs) through alias tables into a ZestEngine material. Colours are converted sRGB to linear (HDR emission colours are stored linear by Unity and are kept), tiling/offset is carried, alpha mode from the shader's mode property (or keywords / render queue), cull mode, cutoff, emission, matcaps, rim, shadow layers, normal map, outline.
  4. Resolve textures: Unity GUIDs are looked up through the .meta files of the folder you point at; the textures are copied to textures/unity/ and given the right import kind with ensure_first_import_for_slot (sRGB colour, normal map). Metallic / smoothness / occlusion are repacked into one ORM texture (R occlusion, G roughness = 1 - smoothness, B metallic). Formats the engine does not load (PSD, TIFF, DDS) are reported.
  5. Write materials/unity/<name>.material and <name>.convert.txt beside it. The report lists Mapped, Approximated, Not supported yet, unmapped properties with a value, and a one-line list of zero / empty ones. Nothing is dropped silently.

Entry points (Files panel context menu): Convert Unity Material... on a .mat, Convert Unity folder... on a directory (task with progress and a summary notification), Import Unity package... on a .unitypackage (gzip tar, read with flate2 already in the tree; extracted to a temp folder, then converted as a folder). The model importer's Search and Remap picks converted materials by name (the .material is named after the Unity material, which is the FBX material name); unity_convert::add_to_model_remap fills the remap table directly.

Unverified

  • Serialised property names for Poiyomi 9/10, Mochie Standard, lilToon and MToon come from the documented labels and naming conventions; the Mochie Standard and Poiyomi blend-mode enum values and the Poiyomi lighting mode order follow the docs' list order. Verify with a real exported avatar and adjust the alias tables (POIYOMI, LILTOON, MTOON in unity_convert.rs).
  • Outline width scale (Poiyomi x5) and the lilToon / MToon rim mappings are approximations. Everything marked Approximated in a report needs a visual check.
  • Unity .mat files that Unity wrote in binary mode are not read.
  • The aliases added for UNITY-3 to UNITY-10 (table above) are likewise names from the shaders' documentation and conventions; lilToon's refraction, _MainTexHSVG, _Shadow3rd*, _MatCap2nd*, _Emission2nd* and _Main2nd* names are the better known ones, the Poiyomi grab pass, flipbook, panosphere, AudioLink, dissolve and decal names are the least certain. A wrong name only means the feature is not carried over and shows in the report as an unmapped property.
  • VRM 0.x vectorProperties colours are read as linear (UniVRM writes them linear); VRM outline widths use a fixed scale (0.002 m, or 0.4 cm in 0.x, is one ZestEngine outline unit).
  • The grab pass was checked in the main viewport pass of a real renderer only. The Toon GRAB distortion direction (normal x to the right, y up on screen) was checked by the seam moving; the VR multiview path was not exercised.

Real-data check (this pass)

Property names were read from .mat files only: a Unity project (~/storage/avis/lemon_meringue, 735 materials, 247 identified as Poiyomi), the Poiyomi 9.3 / 10 / 11 and Mochie 1.65 / 1.69 / 1.75 .unitypackage files and several avatar packages. unity_convert.rs carries real_poiyomi_materials_map_the_verified_names (skipped when the project is absent). Findings: the grab-pass names in the first draft were wrong (_EnableGrabpass, _GrabpassColor, _GrabBlurDistance are the real ones), as were _DissolveCutoff, _FlipbookTex, _FlipbookColumns / _Rows, _PanoRotationSpeed and the AudioLink emission / rim names; decal, detail, panosphere, dissolve and flipbook-enable names were right. The only real grab-pass materials found are Poiyomi preset files (shader guid 0), so the grab mapping is checked on names, not on a shipped avatar. Mochie Screen FX has one real material (the prefab) whose effect toggles are all off, so the effect-amount scales (px per unit) are choices, and the *Model enums are only assumed to be 0 = off. No Mochie Glass or Mochie Standard material exists on the machine.
