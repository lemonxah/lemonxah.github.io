ZestEngine

ZestEngine ECS Guide

How game logic is written in ZestEngine: components hold data, systems hold behaviour, and entities are ready-made objects you can place in a scene or spawn from code. This guide explains the model, then walks through the patterns that real games are made of: moving a player, taking damage, spawning things, picking up coins, opening doors, shooting.

Every example in this guide is compiled and run by crates/zestengine-core/tests/ecs_guide.rs, so the code you copy works. Companion guides: ENGINE_API.md (what you can do from a system: move, spawn, raycast, play sounds, …) and WASM.md (sandboxed scripts for user-generated content). The generated API reference is at api/zestengine_core.

The big picture

ZestEngine's gameplay layer is an entity-component-system built on hecs. The vocabulary maps like this:

ConceptIn ZestEngineWhere
EntityAn object in the scene tree: a transform plus whatever components you attach. Saved with a stable ObjectId (UUID).SceneWorld
ComponentA plain Rust struct implementing TypedComponent: serializable data, shown in the inspector.TypedComponent
SystemA function fn(&SystemWorld, &mut SystemContext) that queries components and changes them.SystemFn
StageThe point in the frame a system runs: Start, FixedUpdate, Update, Gameplay, LateUpdate, Events.Stage
CommandA request that changes the wider world (spawn, destroy, play a sound, load a scene). Queued by systems, applied at the end of the stage.ComponentCommand
EventA value any system can broadcast (ctx.emit) and any system can read next frame (ctx.events).SystemContext
Entity templateA named, ready-made object (mesh shape + starting components) registered by your project.EntityTemplate

A word on naming. In ECS terms every scene object is an entity. In the New Rust menu, Entity means the ready-made kind: a template such as "Enemy" or "Crate" that appears under Create → Entity and can be spawned from code. This guide says object for the scene-tree thing and entity for the template.

Three rules shape everything else:

  1. Data lives in components, behaviour lives in systems. A component never has an update method that the engine calls. Systems find components by querying for them.
  2. Systems edit component data directly; they ask for everything else. Changing a Transform or a Health is an ordinary write. Spawning, destroying, sounds, scene loads and physics pushes are queued as commands, so the world never changes underneath a running query.
  3. Systems run only while playing. The editor's Play mode and a shipped game run the same loop. While you author a scene, nothing ticks.

Objects

An object is a hecs entity carrying a fixed set of built-in components, plus the ones you attach:

Built-in componentMeaning
ObjectIdStable UUID. Saved in scenes, used by ObjectRef fields and the network. Survives reloads and reordering.
NameThe display name. Cosmetic: not unique.
TransformLocal translation / rotation / scale (relative to the parent).
ParentThe parent object, if any.
EnabledThe checkbox in the inspector.
ActiveEnabled and every ancestor enabled. Computed; skip objects where it is false.
GlobalTransformWorld matrix as of the last hierarchy propagation (a snapshot, refreshed at each stage boundary).
OwnerThe object a component instance belongs to. Objects own themselves.

Two details matter in practice.

Local versus world. Transform is local. When you need a true world position, ask the host (host.world_position(), host.position_of(target)) or world.world_transform(entity), which folds in every parent including writes made earlier in the same stage. GlobalTransform is only a snapshot.

Duplicate components. An object can carry two components of the same type. The first lives on the object's own hecs entity; later ones live on small auxiliary entities that point back with Owner. That is why systems query (&Owner, &T) rather than &T: Owner is how you get from a component back to its object (for the transform, the Active flag, the ObjectId).

for (_, (owner, rotator)) in world.query::<(&Owner, &Rotator)>().iter() {
    let object: hecs::Entity = owner.0;            // the object this Rotator is on
    let id = world.object_id(object);              // its saved ObjectId
}

You almost never build objects by hand in game code. The editor builds them from scenes, and systems spawn them with commands (see Spawning and destroying). Tests use SceneWorld directly (see Testing systems).

Components

A component is a struct that implements TypedComponent. It must be Serialize + Deserialize + Default + Send + Sync + 'static.

use serde::{Deserialize, Serialize};
use zestengine_core::TypedComponent;

/// Spins the object around the Y axis.
#[derive(Serialize, Deserialize)]
pub struct Rotator {
    pub degrees_per_second: f32,
}

impl Default for Rotator {
    fn default() -> Self { Self { degrees_per_second: 45.0 } }
}

impl TypedComponent for Rotator {
    const NAME: &'static str = "Rotator";
}

Rules of thumb:

  • NAME is permanent. It is the identity used by the Add Component menu, the .scene file and event bindings. Renaming it orphans saved data. If you must, keep the old one in ALIASES.
  • Saved versus runtime fields. Everything that is not #[serde(skip)] is saved in the scene and shown in the inspector. Mark scratch state (timers, "have I started", cached positions) #[serde(skip)]; it keeps its value while playing and resets when a plugin reloads or a scene loads.
  • Vectors. The workspace builds glam without its serde feature, so saved fields use arrays ([f32; 3]) and runtime-only fields use Vec3/Quat with #[serde(skip)].
  • References to other objects are ObjectRef fields (ObjectRef::NONE when unset). The inspector renders a drop target; at runtime you resolve it with host.get::<T>(self.target), host.position_of(self.target), and so on. They return None when the target is unset or was deleted, so always handle that case.
  • Add #[serde(default)] to a component's struct when you expect to add fields later: old scenes keep loading.
  • Network role. const NET_ROLE (default Both) says where a type exists: Client types are stripped from a dedicated server, Server types from players.
  • Disabled instances. Switching a component off in the inspector moves its value into a DisabledComponent<T> column. Ordinary T queries (and register_system_for::<T>) see only enabled instances; the value, including runtime state, is kept for when it is switched back on.

Register the type so scenes can load it and systems can query it:

registry.register_ecs::<Rotator>();   // `register::<T>()` is the same call

Actions and properties

Components can expose actions (functions) and properties (readable values) to the editor's event bindings: "when the player enters this trigger, call Door → Open". Declare them as static tables and implement three methods. This is also what makes a component callable from a WASM script.

use zestengine_core::{ActionCtx, ActionDesc, ActionType, ArgValue, ParamDesc, PropertyDesc};

static DOOR_ACTIONS: &[ActionDesc] = &[
    ActionDesc::new("Open", "Open", &[], true),
    ActionDesc::new("Close", "Close", &[], true),
    ActionDesc::new("SetSpeed", "Set Speed", &[ParamDesc::float("speed", 2.0)], true),
];
static DOOR_PROPERTIES: &[PropertyDesc] = &[PropertyDesc::new("open", ActionType::Bool)];

impl TypedComponent for Door {
    const NAME: &'static str = "Door";

    fn actions(&self) -> &'static [ActionDesc] { DOOR_ACTIONS }
    fn properties(&self) -> &'static [PropertyDesc] { DOOR_PROPERTIES }

    fn read_property(&self, property: &str) -> Option<ArgValue> {
        (property == "open").then_some(ArgValue::Bool(self.wants_open))
    }

    fn invoke_action(&mut self, _ctx: &mut ActionCtx<'_>, action: &str, args: &[ArgValue]) -> Result<(), String> {
        match action {
            "Open" => self.wants_open = true,
            "Close" => self.wants_open = false,
            "SetSpeed" => self.speed = args[0].as_f32().max(0.0),
            _ => return Err(zestengine_core::actions::unknown_action(Self::NAME, action)),
        }
        Ok(())
    }
}
  • An action's name is permanent for the same reason NAME is; the label is what the editor shows.
  • The last argument of ActionDesc::new is ugc_safe. Mark an action safe only if it cannot change scenes, hurt other players or leave the world. The editor's content-authoring dropdowns offer only safe actions, and sandboxed WASM modules in untrusted content can expose only safe ones; mods may additionally call only the actions the game's allow-list names. See ugc_safe in the WASM Guide for exactly what is enforced where.
  • Arguments arrive already coerced to the declared types and as long as the parameter list, so args[0] is safe to index.
  • An action cannot read itself back through a property reader while it runs, but it can read other components, including other instances of its own type. ctx.emit(event) and ctx.commands work inside actions.

Editor inspector and gizmo

A component's inspector UI and viewport gizmo live in the editor crate (Inspect, Gizmo) behind the plugin's editor cargo feature, so a shipped game never links egui. The New Rust → Component template generates both (see Plugins in a project).

Systems

A system is a plain function. It receives a read-only view of the world (components are borrowed through it) and a per-frame context.

use glam::Quat;
use zestengine_core::Transform;
use zestengine_core::ecs::{Owner, Stage, SystemContext, SystemWorld};

fn rotate(world: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    for (_, (owner, rotator)) in world.query::<(&Owner, &Rotator)>().iter() {
        if !ctx.is_active(world, owner.0) { continue; }
        let mut transform = world.get_mut::<Transform>(owner.0).expect("every object has a Transform");
        let step = Quat::from_rotation_y(rotator.degrees_per_second.to_radians() * ctx.dt);
        transform.rotation = (step * transform.rotation).normalize();
    }
}

Register it on the ComponentRegistry, together with its component:

pub fn register(registry: &mut ComponentRegistry) {
    registry.register_ecs::<Rotator>();
    registry.register_system_for::<Rotator>("game::rotate", Stage::Update, rotate);
}
RegistrationRuns the system
register_system(name, stage, f)Every time the stage runs.
register_system_for::<T>(name, stage, f)Only while at least one enabled T exists. Use this by default: unused features cost nothing.
register_system_if(name, stage, f, condition)Only while condition(world) is true. Used for start-up work (see Timers and state).

Names are unique. Registering an existing name replaces the code and stage in place (that is how a hot-reloaded plugin supersedes its old build). The function type is a plain fn pointer, so a system cannot capture variables: keep state in components, not in closures. (A non-capturing closure, like the |world, ctx| run_ordered(...) forms below, coerces to a fn.)

The comfortable way: run_ordered and EcsMoveHost

Most gameplay code wants "for each active instance of my component, in scene order, with helpers for this object". That is run_ordered, which gives your closure the component and an EcsMoveHost: the per-object toolbox for moving, reading other objects, spawning, physics queries, sounds and more. It also dereferences to the SystemContext, so host.dt, host.input and host.emit(..) all work.

use glam::Vec3;
use zestengine_core::MoveHost;                       // translation(), set_translation(), world_position(), …
use zestengine_core::ecs::{EcsMoveHost, run_ordered};

#[derive(Serialize, Deserialize)]
pub struct PlayerMover {
    pub speed: f32,
}

impl PlayerMover {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        let direction = host.input.axis2("Move"); // x = right, y = forward
        let step = Vec3::new(direction.x, 0.0, -direction.y) * self.speed * host.dt;
        let position = host.translation() + step;
        host.set_translation(position);
    }
}

registry.register_system_for::<PlayerMover>("game::player_mover", Stage::Update, |world, ctx| {
    run_ordered(world, ctx, PlayerMover::update)
});

run_ordered does three things a hand-written loop does not:

  • skips inactive objects (disabled, or under a disabled parent);
  • iterates in scene order, so behaviour is deterministic. That matters for networking, prediction replay and anything where two objects interact within one frame. A bare world.query iterates in archetype order, which is an implementation detail;
  • hands you an EcsMoveHost bound to the object.

Use a bare query when order is irrelevant and you have thousands of instances (it avoids collecting and sorting); use run_ordered otherwise. The full method list of EcsMoveHost is in ENGINE_API.md.

Borrowing rules

hecs checks borrows at run time, per component column, and the engine adds a lock for structural changes. The rules that matter:

  • Two borrows of the same component type conflict if either is mutable. world.get_mut::<Transform>(e) inside a query that already borrows Transform panics with … already borrowed. Nested queries are fine when they borrow different components (the poison zone example below).
  • No structural changes inside a system. You cannot insert, remove or despawn components or objects through the world while a system runs. The world is locked, and the call panics with structural ECS access while component views are borrowed. Spawn and destroy with commands.
  • Use the SystemWorld you were given. Editor-style component views (SceneWorld::get, ComponentSet::get_typed) panic inside a system with component-view access during native ECS execution.
  • A panic in a system is not swallowed. Locks are released and component values stay intact, but the panic propagates, so treat expect like any other assertion.

When two of your own systems need the same data, run them in different stages or let one emit an event for the other (see Events).

Stages

A frame runs the stages in this order. After each stage the engine applies the commands it queued.

tick(dt)
 ├─ Start          repeats (up to 8×) while start-up work keeps spawning objects
 ├─ animation markers ──▶ Events stage (SceneEvent::Animation)
 ├─ FixedUpdate  ┐ 0 to 8 times per frame at a fixed 60 Hz, dt = 1/60
 │  physics step ┘
 ├─ contacts ───────────▶ Events stage (SceneEvent::Contact, 3D then 2D)
 ├─ Update
 ├─ Gameplay
 ├─ navigation agents move, animators evaluate
 └─ LateUpdate
StageUse it for
StartInitialising new instances: capture a rest position, cache a reference, spawn initial children. Not called "once" by the engine: guard with a flag (see Timers and state).
FixedUpdateContinuous forces and anything that must match the physics rate. Runs before each physics step with dt = 1/60.
UpdateMovement and general per-frame logic: controllers, AI steering, input handling.
GameplayLogic that must see movement already resolved: weapons, damage, pickups, health. Runs after Update's movement commands (a character move, a teleport) have been applied.
LateUpdateThings that read the final pose of the frame: cameras following a target, HUD bindings. Runs after animation and navigation.
EventsReacting to contacts and animation markers through ctx.services.scene_events. Runs when such events exist.

ctx.dt is unscaled_dt × time_scale, and the engine clamps a single frame to 0.25 s so a hitch cannot teleport everything.

Commands

Anything that reaches outside component data is a ComponentCommand pushed onto ctx.commands. The engine applies them, in order, right after the stage that queued them:

ctx.commands.push(ComponentCommand::Destroy(object_id));
ctx.commands.push(ComponentCommand::PlaySound { clip: "audio/pop.ogg".into(), position: None, volume: 1.0 });

EcsMoveHost wraps the common ones in readable methods (host.destroy(target), host.play_sound_at(..), host.add_impulse(..)), which is usually what you want. Two properties to remember:

  • Queued means "after this stage". host.destroy_self() does not remove the object while your system is still iterating; it disappears when the stage ends. Systems later in the same stage still see it.
  • Bad targets are ignored. A command that names an object that no longer exists does nothing.

Direct writes to component data (host.edit::<T>(target, |t| ..), host.set_translation(..)) are immediate and visible to systems that run later in the same stage. The full list of commands and which host methods queue them is in ENGINE_API.md.

Events

There are three ways for systems to react to something that happened.

Broadcast events

Any 'static type is an event. A system emits one; every system can read it next frame. The sender and the receiver never touch each other's data, which is the whole point.

/// Event: something hit `target` for `amount`.
pub struct Hit { pub target: ObjectId, pub amount: f32 }
/// Event: the object ran out of hitpoints.
pub struct Died { pub object: ObjectId }

#[derive(Serialize, Deserialize)]
pub struct Hitpoints { pub current: f32, pub max: f32 }   // Default: 100 / 100

fn apply_hits(world: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    // Events emitted during the previous frame are readable now.
    let hits: Vec<&Hit> = ctx.events::<Hit>().collect();
    if hits.is_empty() { return; }
    for (_, (owner, hp)) in world.query::<(&Owner, &mut Hitpoints)>().iter() {
        let Some(me) = world.object_id(owner.0) else { continue };
        let before = hp.current;
        for hit in hits.iter().filter(|hit| hit.target == me) {
            hp.current = (hp.current - hit.amount).max(0.0);
        }
        if before > 0.0 && hp.current == 0.0 {
            ctx.emit(Died { object: me }); // readable next frame
        }
    }
}

fn remove_the_dead(_: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    for died in ctx.events::<Died>() {
        ctx.commands.push(ComponentCommand::Destroy(died.object));
    }
}

registry.register_system_for::<Hitpoints>("game::apply_hits", Stage::Gameplay, apply_hits);
registry.register_system("game::remove_the_dead", Stage::Gameplay, remove_the_dead);

An event emitted in frame N is readable throughout frame N + 1; an event you emit is not visible to you in the same frame. The engine's own systems use the same bus: weapons emit DamageEvent, health emits DeathEvent, target dummies emit ScoreEvent, animators emit AnimatorStateChanged and AnimationEvent, and the HUD reads them. Subscribing to those from your own systems is just ctx.events::<DamageEvent>().

Scene events: contacts and animation markers

Collisions, trigger overlaps and animation markers arrive within the frame in the Events stage, as ctx.services.scene_events:

use zestengine_core::ecs::{ContactPhase, SceneEvent};

#[derive(Default, Serialize, Deserialize)]
pub struct Collector {}                       // marker: can pick coins up

#[derive(Serialize, Deserialize)]
pub struct Coin { pub value: u32 }            // Default: value 1

/// Event: `by` picked up something worth `value`.
pub struct Collected { pub by: ObjectId, pub value: u32 }

registry.register_system_for::<Coin>("game::coin_pickup", Stage::Events, |world, ctx| {
    let contacts = ctx.services.scene_events;
    run_ordered(world, ctx, |coin: &mut Coin, host| {
        let me = host.self_id();
        for contact in contacts {
            if let SceneEvent::Contact { object, other, trigger: true, phase: ContactPhase::Enter, .. } = contact
                && *object == me
                && host.get::<Collector>(*other).is_some()
            {
                host.emit(Collected { by: *other, value: coin.value });
                host.destroy_self();
            }
        }
    })
});

Both objects of a touching pair receive a Contact event (object is the receiver, other the one it touched), with phase Enter, Stay (2D) or Exit, trigger telling a trigger overlap from a solid collision, and two_dimensional for 2D physics. The coin needs a collider with Is Trigger on; the player needs a collider and a rigid body or character.

Action bindings

The third way is data-driven: the inspector's Trigger Events, Interactable, UI Button and Animation Event Bindings components store lists of "call this action on that component" and the engine resolves and runs them. You get that for free for any component that declares actions. Gameplay that fires a binding from code uses queue_actions(&bindings, &FireSource { … }, ctx.commands).

Spawning and destroying

Spawning is a command; the call returns the new ObjectId immediately so you can wire it up, but the object exists from the next stage on.

let id = host.spawn_prefab("prefabs/enemy.prefab", position, rotation); // a .prefab asset
let id = host.instantiate(self.bullet_template, position, rotation);    // clone a scene object
let id = host.spawn_entity("Crate", position, rotation);                // a registered entity
host.net_spawn("prefabs/bullet.prefab", position, rotation);            // on every peer
host.destroy(target);                                                    // object and children
host.destroy_self();
host.set_active(door, false);                                            // disable without deleting

A timed self-destruct is the smallest useful spawn companion:

#[derive(Serialize, Deserialize)]
pub struct Lifetime { pub seconds_left: f32 }   // Default: 3.0

impl Lifetime {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        self.seconds_left -= host.dt;
        if self.seconds_left <= 0.0 {
            host.destroy_self();
        }
    }
}

Objects spawned during a frame run their Start systems before the next Update, so a freshly spawned object is initialised before it acts. See Entities for a spawner that drops crates.

Entities

An entity is a named, ready-made object: a mesh shape plus the components it starts with. Register it once; it then appears under Create → Entity in the editor and any system can spawn it by name.

use zestengine_core::ecs::{EntityShape, EntityTemplate};

/// The entity: a cube that deletes itself after ten seconds.
fn crate_entity() -> EntityTemplate {
    EntityTemplate::new(EntityShape::Cube).with(Lifetime { seconds_left: 10.0 })
}

registry.register_entity("Crate", crate_entity);
  • EntityShape is Empty, Cube, Sphere, Capsule or Plane. Empty makes a transform that only carries components (a spawner, a manager); the others also get a MeshRenderer with the default material.
  • .with(component) adds a component. Add as many as you like, in inspector order. The builder function runs for every new instance, so each object gets its own component values.
  • The name is the identity: spawn_entity("Crate", ..) and the menu both use it. Registering an existing name replaces the builder, and a plugin reload drops entities the plugin no longer exports.
  • An entity made in the editor is an ordinary scene object once placed: it saves as its components and mesh, and you can edit it freely.
  • On a dedicated server (no renderer) an entity still spawns, with its components and without a GPU mesh.

A spawner is just a component and a system:

#[derive(Serialize, Deserialize)]
pub struct CrateSpawner {
    pub every: f32,
    #[serde(skip)]
    pub timer: f32,
}

impl CrateSpawner {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        self.timer -= host.dt;
        if self.timer <= 0.0 {
            self.timer = self.every;
            let above = host.world_position() + Vec3::Y;
            host.spawn_entity("Crate", above, Quat::IDENTITY);
        }
    }
}

Talking to other objects

Systems often need another object's data: a follower needs its target's position, a turret needs its target's health. Reference the other object with an ObjectRef field and ask the host.

#[derive(Serialize, Deserialize)]
pub struct Follower {
    pub target: ObjectRef,
    pub speed: f32,
}

impl Follower {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        let Some(goal) = host.position_of(self.target) else { return }; // world position
        let here = host.world_position();
        let to_goal = goal - here;
        let step = self.speed * host.dt;
        if to_goal.length() <= step {
            host.set_world_position(goal);
        } else {
            host.set_world_position(here + to_goal.normalize() * step);
        }
    }
}

When one component should act on every object of another kind, query both. This swamp hurts anything with Hitpoints inside its radius; the nested query is legal because the two loops borrow different components:

fn poison(world: &SystemWorld<'_>, ctx: &mut SystemContext<'_>) {
    for (_, (owner, zone)) in world.query::<(&Owner, &PoisonZone)>().iter() {
        if !ctx.is_active(world, owner.0) { continue; }
        let Some(center) = world.world_transform(owner.0).map(|m| m.w_axis.truncate()) else { continue };
        for (_, (victim, hp)) in world.query::<(&Owner, &mut Hitpoints)>().iter() {
            let Some(at) = world.world_transform(victim.0).map(|m| m.w_axis.truncate()) else { continue };
            if at.distance(center) <= zone.radius {
                hp.current = (hp.current - zone.damage_per_second * ctx.dt).max(0.0);
            }
        }
    }
}

Input

Input is a snapshot of actions (named, rebindable), not raw keys: ctx.input is an InputState.

CallMeaning
input.down("Fire")Held this frame.
input.pressed("Fire")Went down this frame (edge).
input.released("Fire")Went up this frame (edge).
input.axis("Throttle")1D value, −1 to 1 (0/1 for a button).
input.axis2("Move")2D value. x is right, y is forward.

The default keyboard-and-mouse scheme defines Move (WASD), Look (mouse), Jump, Sprint, Crouch, Fire, Interact, Grab and Voice; the gamepad scheme uses the same names on its sticks and buttons, so code written against action names works on every device. Players can rebind them, and a game can define its own actions in its control scheme. An action that does not exist reads as "not pressed". When the player is typing into a UI text field, host.ui_text_editing() is true: skip gameplay input then.

For networked objects another peer may be driving, check host.driven_remotely() before applying local input, and host.has_authority(id) before changing shared state.

Physics and contacts

Physics queries are immediate; pushes are commands. A ray gun:

#[derive(Serialize, Deserialize)]
pub struct Laser { pub damage: f32, pub range: f32 }   // Default: 25 / 100

impl Laser {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        if !host.input.pressed("Fire") { return; }
        let aim = host.self_transform(); // world position and orientation
        let Some(hit) = host.raycast(aim.translation, aim.forward(), self.range) else { return };
        let damage = self.damage;
        host.edit::<Hitpoints>(hit.object, move |hp| hp.current = (hp.current - damage).max(0.0));
        host.add_impulse(hit.object, aim.forward() * 5.0);
        host.play_sound_at("audio/zap.ogg", hit.point, 1.0);
    }
}

host.raycast ignores triggers and the caller's own colliders; use raycast_filtered with a RayFilter for layer masks. Rigid bodies move through commands (add_force, add_impulse, set_velocity); characters through move_character. Contacts arrive as scene events. The ENGINE_API guide covers physics in full.

Timers and state

Three patterns cover most state.

A cooldown is a #[serde(skip)] float you count down, as in CrateSpawner::timer above.

A state machine is an enum field. Derive Serialize, Deserialize on the enum and give the component a Default; match on it in the system and change it as conditions are met.

Start-up work uses the Start stage. The engine does not call "start once per instance"; the stage simply runs before Update each frame, and your component remembers whether it has initialised. Register the system with register_system_if so it costs nothing once every instance has started:

#[derive(Serialize, Deserialize)]
pub struct Door {
    pub lift: f32,
    pub speed: f32,
    #[serde(skip)]
    pub wants_open: bool,
    #[serde(skip)]
    pub closed_y: Option<f32>,        // None until started
}

impl Door {
    /// Runs once for each new instance (Stage::Start): remember where "closed" is.
    fn start(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        if self.closed_y.is_none() {
            self.closed_y = Some(host.translation().y);
        }
    }

    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        let Some(closed) = self.closed_y else { return };
        let goal = if self.wants_open { closed + self.lift } else { closed };
        let mut position = host.translation();
        let step = self.speed * host.dt;
        position.y += (goal - position.y).clamp(-step, step);
        host.set_translation(position);
    }
}

registry.register_system_if(
    "game::door_start",
    Stage::Start,
    |world, ctx| run_ordered(world, ctx, Door::start),
    |world| world.query::<&Door>().iter().any(|(_, door)| door.closed_y.is_none()),
);
registry.register_system_for::<Door>("game::door", Stage::Update, |world, ctx| {
    run_ordered(world, ctx, Door::update)
});

The Door of the actions example is this same component: Open and Close set wants_open, and any trigger, button or WASM script can bind to them.

Showing state in the UI

UI elements are components too, so a system updates them like any other data:

/// Shows the score in this object's `UiText`.
#[derive(Default, Serialize, Deserialize)]
pub struct ScoreBoard {
    #[serde(skip)]
    pub score: u32,
}

impl ScoreBoard {
    fn update(&mut self, host: &mut EcsMoveHost<'_, '_>) {
        for collected in host.events::<Collected>() {
            self.score += collected.value;
        }
        let id = host.self_id();
        let text = format!("Score {}", self.score);
        host.edit::<UiText>(id, move |ui| ui.text = text);
    }
}

registry.register_system_for::<ScoreBoard>("game::score_board", Stage::LateUpdate, |world, ctx| {
    run_ordered(world, ctx, ScoreBoard::update)
});

LateUpdate is the right stage for anything that mirrors the frame's final state onto the screen.

Plugins in a project

Your game's components, systems and entities live in a Rust crate, plugins/components, that the editor builds and hot-reloads and a shipped game links. Files panel → Create → New Rust adds to it:

Menu itemWritesRegisters with
New Rust → Componentsrc/components/new_component.rs: data struct, TypedComponent impl, inspector and gizmo stubsregistry.register_ecs::<T>() and the editor traits
New Rust → Systemsrc/systems/new_system.rs: a system function with a query skeletonregistry.register_system(..)
New Rust → Entitysrc/entities/new_entity.rs: an EntityTemplate builderregistry.register_entity(..)

Each press creates the next free name (new_component, new_component_1, …), opens the file, and wires it into lib.rs. A fresh plugin crate looks like this (the orbit and orbiter files are a working starter that shows the three kinds side by side):

plugins/components/
├── Cargo.toml
└── src/
    ├── lib.rs                 ← consolidates everything into the game
    ├── components/orbit.rs    ← data: the Orbit component (+ inspector)
    ├── systems/orbit.rs       ← behaviour: moves every Orbit
    └── entities/orbiter.rs    ← a ready-made sphere that carries an Orbit

lib.rs is the one place that hands every component, system and entity to the engine:

mod components {
    pub mod orbit;
    // zestengine: new component modules here
}
mod systems {
    pub mod orbit;
    // zestengine: new system modules here
}
mod entities {
    pub mod orbiter;
    // zestengine: new entity modules here
}

zestengine_core::export_plugin_abi!();

#[unsafe(no_mangle)]
pub fn zestengine_register(registry: &mut ComponentRegistry) {
    // Components: data attached to objects.
    components::orbit::register(registry);
    // zestengine: new components register here

    // Systems: behaviour that runs every frame over component data.
    systems::orbit::register(registry);
    // zestengine: new systems register here

    // Entities: ready-made objects (Create > Entity, `spawn_entity`).
    entities::orbiter::register(registry);
    // zestengine: new entities register here
}

The // zestengine: comments are anchors the menu inserts above; leave them in place. Each module exports its own register function, so lib.rs never names the types inside: rename a struct freely, and when you rename or move a file just update its two lines in lib.rs. A plugin crate made before this layout keeps working: the menu falls back to flat modules next to lib.rs and registers them at the top of zestengine_register.

How a plugin gets into the game:

  • In the editor, Tools → Build & Reload Components compiles the crate with its editor feature and registers the new build over the old one. Component values are re-created from their serialized state, so #[serde(skip)] runtime fields reset on reload.
  • In a shipped game, src/main.rs calls zestengine_project_components::zestengine_register(registry) from run_game, linking the plugin statically (the editor feature, egui and the editor crate are not linked).
  • On a dedicated server, the built cdylib is listed in server.ron and loaded at start-up.
  • ABI stamp. export_plugin_abi!() lets a host refuse a plugin built with a different rustc, engine version or dependency features instead of crashing. Rebuild plugins and the engine together.

Testing systems

Systems are plain functions over a world, so they test without a window, a GPU or the engine loop. Build a SceneWorld, register your component and systems on a ComponentRegistry, run a stage, and look at the data and the queued commands. This is the harness the examples in this guide use:

use zestengine_core::ecs::{SceneEvent, SceneWorld, Stage, SystemContext};
use zestengine_core::{AnyBox, ComponentCommand, ComponentRegistry, InputState};

#[derive(Default)]
struct Frame {
    dt: f32,
    input: InputState,
    events: Vec<AnyBox>,
    scene_events: Vec<SceneEvent>,
}

/// Run every system registered for `stage` once and return the commands they queued.
fn run(registry: &ComponentRegistry, scene: &SceneWorld, stage: Stage, frame: &Frame) -> Vec<ComponentCommand> {
    let mut commands = Vec::new();
    let mut ctx = SystemContext::new(&frame.input, &mut commands);
    ctx.dt = frame.dt;
    ctx.services.events = &frame.events;
    ctx.services.scene_events = &frame.scene_events;
    registry.run_systems(stage, scene, &mut ctx);
    commands
}

#[test]
fn spins_active_objects_only() {
    let mut registry = ComponentRegistry::default();
    register(&mut registry);
    let mut scene = SceneWorld::new();
    let spinning = scene.spawn("Spinning");
    scene.insert(spinning, Rotator { degrees_per_second: 90.0 }).unwrap();
    run(&registry, &scene, Stage::Update, &Frame { dt: 1.0, ..Default::default() });
    let expected = Quat::from_rotation_y(90f32.to_radians());
    assert!(scene.get::<Transform>(spinning).unwrap().rotation.abs_diff_eq(expected, 1e-5));
}

Useful pieces:

  • SceneWorld::spawn, insert, get, get_mut, remove, set_parent, propagate build and inspect scenes. After changing a parent or Enabled flag, call propagate() so Active and GlobalTransform update, as the engine does at stage boundaries.
  • Events: set ctx.services.events = &[AnyBox(Box::new(Hit { … }))] to simulate last frame's broadcasts, and ctx.services.scene_events for contacts. Read what your system emitted from commands (ComponentCommand::Emit).
  • Services: set ctx.services.physics = Some(&mock) with your own PhysicsQuery to fake raycasts (the Laser test does this), nav, screen and net likewise.
  • Actions: call component.invoke_action(&mut ActionCtx { … }, "Open", &[]) directly.
  • Multi-frame behaviour: call run in a loop and assert after each step; commands queued by one frame are not applied by the harness, so assert on them instead.

Common mistakes

SymptomCause and fix
Panic: … already borrowedTwo borrows of one component type, one mutable (often get_mut::<Transform> inside a query that has &mut Transform). Query different components, or collect first.
Panic: structural ECS access while component views are borrowedInserting, removing or despawning inside a system. Queue a command.
System never runsNot registered (add it to zestengine_register), registered with register_system_for::<T> while no enabled T exists, or the object is inactive (disabled or under a disabled parent).
Component missing from the Add menu or lost from scenesregister_ecs::<T>() not called, or NAME changed.
Object is in the wrong place under a parentA world position written to the local Transform. Use set_world_position / set_world_position_of.
Spawned object not found next lineSpawns are commands; it exists from the next stage. Keep the returned ObjectId.

Behaviour differs per frame rateMultiplying by a constant instead of ctx.dt.
